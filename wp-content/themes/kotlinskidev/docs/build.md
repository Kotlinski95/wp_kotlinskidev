# Build System Architecture

## Current setup

The theme uses `@wordpress/scripts` (which wraps Webpack + Babel + TypeScript + SCSS
compilation) with a customized `webpack.config.js`. Key facts:

- **Entry points**: one Webpack entry per block/script module, defined explicitly in
  `webpack.config.js` (`main`, `critical`, `editor`, and one entry per block —
  `banner-carousel`, `gallery-lightbox`, `content-tabs`, etc.). Adding a new block means
  adding a new entry here.
- **Output**: split by asset type — `build/js/[name].js` + `build/js/[name].asset.php`
  (dependency array + content-hash version, produced automatically by
  `@wordpress/dependency-extraction-webpack-plugin`, deliberately co-located with its
  `.js` — see Non-negotiables) and `build/css/[name].css` + `build/css/[name]-rtl.css`
  (block `style.scss` output). `build/blocks/<name>/` (block.json + render.php copies)
  and `build/images/` are separate, pre-existing mechanisms, untouched by this split.
- **`tsconfig.json`**: `outDir` points at `./build/` too (this is mostly informational —
  actual emission is done by Webpack/Babel, not `tsc`; `tsc` is used for type-checking).
- **PHP consumption**: `functions/*.php` modules go through two helpers in
  `functions/asset-paths.php` — `kotlinskidev_build_path('js'|'css', $file)` (filesystem
  path) and `kotlinskidev_build_url('js'|'css', $file)` (enqueue URL) — in ~35 call
  sites across 9 files, rather than hardcoding `get_template_directory_uri() . '/build/...'`
  directly. Several of these are not simple enqueues:
  - `defer_global_css()` reads `build/css/main.css` and its `filemtime()` for cache-busting.
  - `kotlinskidev_breakpoint_swap_inline_style_paths()` rewrites inline `<style>` URLs
    to point at breakpoint-specific transformed files inside `build/` (subfolder-agnostic,
    see Non-negotiables).
  - Critical-path inlining reads `build/css/critical.css` and `build/js/critical.js` as
    raw file contents and echoes them inline in `<head>` for above-the-fold performance.
  - Editor and per-block enqueues `include` the generated `*.asset.php` files to get
    the dependency array + version hash for `wp_enqueue_script`/`wp_enqueue_style`.
  - `src/blocks/*/block.json` (37 files) reference compiled output directly via
    `file:../../../build/js/<name>.js` / `build/css/<name>.css`, resolved by WordPress
    core's own block.json loader, not by PHP in this theme.
- **Not committed**: `build/` is git-ignored at the WordPress-root `.gitignore`
  (`# Ingore build folders` / `build`). CI/deploy must run `npm run build` before
  shipping (see README "Deployment").

## Why Astra's `assets/css/{minified,unminified}` pattern doesn't fit here

Astra ships **prebuilt, hand-authored** CSS/JS in its repo because it's distributed
through wp.org — end users install a zip and never run a build step. Its
`assets/css/minified` + `assets/css/unminified` split exists so `SCRIPT_DEBUG` can pick
the readable version for support debugging, and both are committed to version control.
There is no dependency-extraction manifest (`.asset.php` equivalent) — Astra
hand-maintains cache-busting version numbers in PHP.

kotlinskidev is the opposite kind of theme: a **privately deployed, build-pipeline-driven**
theme where `build/` is deliberately git-ignored and regenerated by CI on every deploy.
Copying Astra's structure would mean:

- Giving up `.asset.php` auto-generated dependency arrays + content-hash versioning
  (you'd hand-maintain versions like Astra does — a regression, not an improvement).
  A custom Webpack `output.path` per asset type (e.g. `assets/css/` vs `assets/js/`)
  actively fights `@wordpress/dependency-extraction-webpack-plugin`, which expects the
  `.asset.php` file to sit next to its `.js`/`.css` sibling.
- Re-plumbing ~35 call sites in `functions/*.php` that hardcode `/build/...` paths,
  including three non-trivial ones (critical CSS/JS inlining, breakpoint style-path
  swapping, cache-busting via `filemtime()`).
- Committing generated output to git, which this project's CLAUDE.md/README
  explicitly reject ("`build/` output is never committed").

**Conclusion: keep `build/` as the single Webpack output directory.** It is already
the correct pattern for a build-tooled, non-wp.org-distributed theme. Renaming it to
mirror Astra would be moving backward, not forward.

## What's actually worth improving

The real pain point isn't the *location* of `build/` — it's that it was a **flat,
138-file directory** with no internal grouping, which made intent hard to read at a
glance and encouraged the copy-paste entry blocks that used to be in
`webpack.config.js`. All three items below are now implemented — kept here as the
record of what was considered and why, in increasing order of how much they touched:

### 1. Group entries by kind, keep the flat output for now

Restructure `webpack.config.js`'s `entry` object into named groups (scripts entry
object built from spreading `coreEntries`, `blockEntries`, `blockInitEntries`) purely
for *source readability* — output path stays `build/[name].js` unchanged. Zero PHP
changes required.

```js
const coreEntries = { main: ..., critical: ..., editor: ..., "admin-bar": ... };
const blockEntries = { "banner-carousel": ..., "content-tabs": ..., ... };
const blockInitEntries = { "banner-carousel-init": ..., "content-tabs-init": ..., ... };

entry: { ...coreEntries, ...blockEntries, ...blockInitEntries },
```

### 2. Auto-generate block entries instead of hand-listing them

Every block already lives at `src/blocks/<name>/index.(ts|tsx)` with an optional
`init.ts`. Replace the hand-written `blockEntries` object with a `glob`-based scan of
`src/blocks/*/index.{ts,tsx}` (and `*/init.ts`), so adding a block's `index.tsx` file
is enough — no `webpack.config.js` edit needed. This directly serves the "easy to
extend" goal without touching output structure or PHP.

### 3. Subfolder `build/` by asset type (`js/`, `css/`) — implemented, see Status below

CSS and JS are now separated *within* `build/` (`build/css/[name].css`,
`build/js/[name].js`). Three separate technical obstacles had to be cleared, not just
one filename option — see Status for what each actually required.

## Non-negotiables to preserve in any change

- `.asset.php` files must stay siblings of their `.js` file — this is not just the
  dependency-extraction plugin's own convention, it's a **hard WordPress core
  requirement**: `register_block_type()` reading a block.json with `file:`-scheme
  `editorScript`/`viewScript` paths auto-discovers dependencies/version by looking for
  a same-directory `.asset.php` with the same basename. Confirmed empirically (see
  Status) — moving `.asset.php` to its own folder silently drops every WP-provided
  script dependency (`react`, `wp-element`, `wp-blocks`, …) for all 37 blocks
  registered this way, with no error, just broken editor JS.
- `build/critical.css` / `build/critical.js` must remain readable as raw file
  contents by `functions.php` (inlined verbatim into `<head>`).
- `kotlinskidev_breakpoint_swap_inline_style_paths()`'s breakpoint-transformed file
  lookup (`kotlinskidev_breakpoint_transformed_file()`) must keep working against
  whatever path scheme is chosen. It already does — that logic operates on whatever
  relative path follows `.../build/`, so it's subfolder-agnostic by construction and
  needed zero changes for the `js/`/`css/` split.
- `build/` stays git-ignored; CI must run `npm run build` before every deploy.
- Update `docs/treeview.md` if `build/`'s *conceptual* structure changes (it documents
  source structure, but flag it if this doc's grouping recommendation is adopted).

## Status: #1 and #2 implemented

`webpack.config.js` now derives `entry` instead of hand-listing every block:

- `coreEntries` stays explicit (`main`, `critical`, `editor`, `admin-bar` — these
  aren't per-block, so there's nothing to derive).
- `blockEntries` is built by scanning `src/blocks/*/` for `index.ts`/`index.tsx`,
  `init.ts`, and `panel.tsx`, generating the `<dir>`, `<dir>-init`, and `<dir>-panel`
  entry keys respectively.
- Block directories whose `index` file is instead imported wholesale into
  `src/editor.ts` or `src/index.ts` (block-extension/filter modules like
  `border-gradient`, `parallax`, `responsive-display`, etc., which register via
  `addFilter` rather than `registerBlockType` and ship inside the `editor`/`main`
  bundle) are detected by parsing those two files' import statements and excluded
  from `blockEntries`, so they aren't double-compiled into their own bundle.

This was verified empirically before landing: the derived entry object was diffed
key-for-key against the old hand-written one (zero mismatches, 45 entries), and a
full `npm run build` was diffed file-for-file against a build from the old config
(140 output files, byte-identical file list, zero diff).

Practical effect: adding a new standalone block now only requires creating
`src/blocks/<name>/index.ts(x)` (plus `init.ts`/`panel.tsx` if needed) — no
`webpack.config.js` edit. Adding a new block-extension/filter module still requires
one line in `editor.ts` or `index.ts`, same as today, and that one line is exactly
what keeps it out of `blockEntries` automatically.

## Status: #3 implemented — `build/js/`, `build/css/`

`build/` root is now empty of loose files: JS bundles + their `.asset.php` manifests
live in `build/js/`, CSS (including `-rtl.css` siblings) in `build/css/`. Per-block
`block.json`/`render.php` copies in `build/blocks/<name>/` (a separate, pre-existing
mechanism — `PhpFilePathsPlugin`/`CopyWebpackPlugin`, untouched) and `build/images/`
are unaffected.

Three things had to change in `webpack.config.js`, not one:

1. **JS**: `output.filename`/`output.chunkFilename` → `js/[name].js`. Trivial.
2. **`.asset.php`**: `DependencyExtractionWebpackPlugin`'s `outputFilename` option set
   to `js/[name].asset.php` — i.e. co-located with JS, **not** its own `php/` folder.
   An initial attempt to give `.asset.php` its own `build/php/` folder was tried and
   empirically reverted after the WP-core sibling-lookup discovery above broke
   dependency resolution for every block.json-registered block (verified via
   `wp eval` against `WP_Block_Type_Registry`: `deps` came back empty and `ver` fell
   back to block.json's static version instead of the content hash).
3. **CSS**: `MiniCssExtractPlugin`'s `filename` option set to `css/[name].css`, plus a
   forked RTL plugin (`bin/webpack/nested-rtlcss-plugin.js`, derived from
   `@wordpress/scripts`'s bundled `rtlcss-webpack-plugin`) — the stock plugin hardcodes
   its output name as flat `[name]-rtl.css` with no directory-prefix option, so without
   the fork every `-rtl.css` file would've landed back at `build/` root regardless of
   where its non-RTL sibling was moved to. The fork derives the target directory from
   the actual source CSS asset's path instead of assuming a flat layout, so it stays
   correct even if the CSS filename template changes again later.

On the PHP side, all ~35 hardcoded `/build/...` references across 9 files
(`functions/cache.php`, `enqueue-scripts.php`, `theme-setup.php`, `modals.php`,
`service-locations.php`, `responsive-display.php`, `admin-bar-styles.php`,
`project-card.php`, `banner-slider.php`, `article-card.php`) now go through two new
helpers in `functions/asset-paths.php` (loaded immediately after `cache.php`):
`kotlinskidev_build_path( 'js'|'css', $filename )` (filesystem path) and
`kotlinskidev_build_url( 'js'|'css', $filename )` (enqueue URL). A future path-scheme
change is now a one-file edit instead of a repo-wide search-and-replace.
`functions/breakpoints.php` needed **no** changes — its style-swap logic already
works on whatever relative path follows `build/`, confirmed by the non-negotiables
note above.

`src/blocks/*/block.json` (37 files) had their `file:../../../build/<name>.js`/`.css`
references updated to `file:../../../build/js/<name>.js` / `build/css/<name>.css`.

Verified via `wp eval` against a real local WordPress install (not just a build diff):
every `kotlinskidev/*` block's `editor_script_handles`/`view_script_handles`/
`style_handles` resolve to an existing file with zero missing assets (0 issues across
all registered blocks); `.asset.php`-derived `deps`/`ver` correctly populated
(spot-checked `banner-carousel`, `article-card`, `scroll-section`); manual enqueues
(`global-style`, `wp-typescript`, `kotlinskidev-editor-only`/`-overrides`) resolve
correctly; critical CSS/JS inlining (`inline_critical_css()`/`inline_critical_js()`)
still emits both `<style id="critical-css">` and `<script id="critical-js">` tags with
real content. One pre-existing dead reference was found and left untouched
(`functions/responsive-display.php` enqueues a `responsive-display.js` bundle that has
never existed in any version of `webpack.config.js`, hand-written or derived — not a
regression from this change, just parity with prior broken behavior, out of scope to
fix here).

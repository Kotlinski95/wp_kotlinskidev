# Storybook

Browse and interact with the theme's custom Gutenberg blocks in isolation, outside the Site Editor. Scope is blocks only — patterns and templates stay PHP+WP-data-bound and aren't represented here.

```bash
npm run storybook          # dev server, http://localhost:6006, hot-reloads on story/component edits
npm run build-storybook    # static build → storybook-static/ (gitignored, not committed)
```

**Restart the dev server only when you edit `.storybook/main.ts` or `.storybook/preview.tsx`.** Everything else — story files, mock files, the blocks themselves — hot-reloads with zero restart.

## Why this needed real work, not just `npx storybook init`

A block theme's blocks are built to run inside a full WordPress admin bootstrap: real REST endpoints, a real Media Library, a real `core/block-editor` registry populated by the real editor's own JS. Storybook provides none of that. Every piece of this setup exists to paper over one specific missing piece of that bootstrap. If you're about to fight a new "works in wp-admin, breaks in Storybook" bug, check the table below first — there's a decent chance it's already solved.

| Missing WP runtime piece | Symptom without a fix | Fix | Where |
|---|---|---|---|
| `@wordpress/data` registry, one instance | `useBlockProps()` throws `Cannot destructure property 'getBlockType' of undefined` | Align `@wordpress/*` devDependencies to one mutually-compatible version set | `package.json` |
| `core-data` store never registered | `select('core').getEntityRecords()` returns `undefined` and crashes | `import "@wordpress/core-data"` (side-effect registration) | `preview.tsx` |
| `wp.media` (Media Library modal) | Block always renders empty, no "Add" button at all | Fake `editor.MediaUpload` filter + `mediaUpload` block-editor setting | `mock-media-upload.tsx` |
| WP REST `block-renderer` endpoint | `ServerSideRender`-backed blocks show `Error loading block: [object Object]` | Alias `@wordpress/server-side-render` to a per-block static-HTML mock | `mock-server-side-render.tsx` |
| `wp_get_global_stylesheet()` (theme.json → CSS vars) | `light-dark()` colors and `--wp--preset--*` vars are empty | Generate the same custom properties from `theme.json` at preview load | `wp-preset-tokens.ts` |
| A block registered via `registerBlockType()` | `useBlockProps.save()` crashes in `extraPropsFromHooks` reading `undefined` supports | `import "./index"` (or equivalent) for its registration side effect | per-story, see below |
| A block's own `style.scss`, only ever imported by that block's `index.ts`/`init.ts` webpack entry | Block renders with correct markup but zero of its own CSS — unstyled links, wrong spacing, no fixed/sticky positioning | `import "./style.scss";` directly in the story file | per-story, see below |

## Architecture

- **`.storybook/main.ts`** — webpack config. Aliases `@utils`/`@node_modules`/`@assets` (mirrors `webpack.config.js`), aliases `@wordpress/server-side-render` to the mock, force-deduplicates `@wordpress/data`+`@wordpress/element` to their top-level copies (see the version-alignment section), adds an SCSS loader rule, and swaps in `@storybook/addon-webpack5-compiler-swc` since Storybook 10's default webpack5 builder doesn't handle `.tsx`/JSX out of the box.
- **`.storybook/preview.tsx`** — global decorator + parameters. Imports the theme's *real* stylesheets (`critical.scss` + `index.scss`, not just editor overrides) plus `@wordpress/block-library`'s compiled CSS for core-block base styles (buttons, images, groups). Registers the `mock-media-upload.tsx` side effect. Defines the light/dark theme toolbar, custom viewport presets, and wraps every story in `SlotFillProvider` + a responsive two-column frame (canvas + `InspectorControls.Slot` sidebar).
- **`.storybook/wp-preset-tokens.ts`** — reads `theme.json` directly and injects `--wp--preset--color--*`/`--gradient--*`/`--spacing--*`/`--font-size--*` custom properties into a `<style>` tag, mirroring what WP core generates server-side. Stays in sync with `theme.json` automatically since it reads the file, not a snapshot.
- **`.storybook/mock-assets.ts`** — named exports of real `assets/images/*.webp` files for reuse as mock content across blocks. Pick images by what they're standing in for, not by "biggest available": `about.webp` (near-square) reads fine as a single article thumbnail but distorts a carousel's fixed-height slide if mixed with wide photos; `hero-background.webp`/`kotlinskidev-background.webp`/`google-map.webp` share a similar wide aspect ratio, meant for anything carousel-shaped.
- **`.storybook/mock-media-upload.tsx`** — see table above.
- **`.storybook/mock-server-side-render.tsx`** — see table above and "Adding a mock for a new `ServerSideRender` block" below.
- **`src/utils/storybook-edit-props.ts`** — shared story helpers, not @wordpress/*-runtime mocks. `getDefaultAttributes(schema)` turns a `block.json` attributes schema into a real default-valued attributes object. `buildEditProps(attributes)` fills in the rest of `BlockEditProps<T>` (clientId, isSelected, context, className) for blocks typed against the full WP shape. `useInteractiveAttributes<T>()` wires a story's args to `setAttributes` via `useArgs()` (real two-way binding — Controls panel edits *and* the block's own UI calling `setAttributes` both work) and logs every call through `storybook/actions`.

## The `@wordpress/*` version-alignment requirement

npm nests a separate copy of a dependency under a package whenever the top-level installed version doesn't satisfy that package's own `package.json` range. `@wordpress/block-editor` internally imports `@wordpress/data` — if the *top-level* `@wordpress/data` version doesn't match what `@wordpress/block-editor` was built against, npm gives `@wordpress/block-editor` its own private nested copy. Two copies of `@wordpress/data` means two separate store registries with no way to talk to each other: `useBlockProps()` (inside `@wordpress/block-editor`, using its nested `@wordpress/data`) registers `core/block-editor` into registry A; your own block code (`import { useSelect } from "@wordpress/data"`, resolving to the top-level copy) reads from registry B, which has nothing registered. Confirmed via `find node_modules/@wordpress -path "*/node_modules/@wordpress/data"` — before alignment, half a dozen packages had their own nested copy.

Fix, in order of preference:

1. **Pin the top-level `@wordpress/*` devDependencies to one mutually-compatible release train** (they're released together as part of Gutenberg; picking versions independently over time is what caused the drift in the first place). This is what's actually pinned in `package.json` today — after aligning, `find` turns up zero nested `@wordpress/data` copies.
2. If a stray nested copy still turns up for some other package, force-dedupe *just that package* via a webpack `resolve.alias` (see `SINGLETON_WORDPRESS_PACKAGES` in `main.ts`) rather than the whole `@wordpress/*` namespace — aliasing indiscriminately re-broke things: `@wordpress/private-apis`' lock/unlock symbol-matching mechanism requires every consumer to share the *exact* module instance a `lock()` call used, and forcing a mismatched top-level version in caused `Cannot unlock an object that was not locked before`.

This alignment is dev-only. It never touches the real site's build — `webpack.config.js`'s `DependencyExtractionWebpackPlugin` externalizes every `@wordpress/*` import to a `wp.*` global regardless of which npm version resolved locally, so the installed version only matters for type-checking and for Storybook.

## Story conventions

- Colocate the story next to the file it documents, named to match: `edit.stories.tsx` next to `edit.tsx`, `index.stories.tsx` next to `index.tsx` (for the ~10 blocks whose `Edit` lives directly in `index.tsx`), `save.stories.tsx` next to `save.tsx` for a frontend-focused preview.
- One `Meta`/title per file. If a file registers two block types (e.g. `social-section` registers both `kotlinskidev/social-section` and `kotlinskidev/social-item`), split into two story files rather than cramming two components under one default export.
- Build args from real data, not hand-typed literals: `getDefaultAttributes<XAttributes>(metadata.attributes)` reads the actual `block.json` defaults, so a future attribute-default change is picked up automatically.
- Make it interactive by default: use `useInteractiveAttributes<T>()` inside a small wrapper component set as the story's `render`, not a static `args.setAttributes: () => {}` no-op. See `article-card/edit.stories.tsx` for the minimal pattern, `banner-carousel/save.stories.tsx` for one with custom `argTypes` too.
- **No inline comments** in story files (repo-wide rule) — story/export names carry the meaning.
- If a block's real markup varies by *external state* rather than by a block attribute (breadcrumbs' trail depends on `is_category()`/`is_single()`/`is_page()`, never on an attribute — its own `ServerSideRender` call doesn't even forward `attributes` to the REST preview), don't try to force it into a Control. Give the mock a React Context instead (see `BreadcrumbsRouteContext` in `mock-server-side-render.tsx`) and write one named story per variant, each setting the Provider's value.

### If the story's `render` needs a Storybook hook (`useArgs`, `useInteractiveAttributes`)

Storybook only wires its hooks context around the function passed *directly* as `render` — the one it calls itself. Wrapping that hook call in a JSX-nested child component instead (`render: () => <MyComponent />`, where `MyComponent` calls `useInteractiveAttributes()`) throws `Storybook preview hooks can only be called inside decorators and story functions`, because React invokes `MyComponent` as a normal child render, not as "the story function" Storybook wrapped. Fix: pass the component itself as `render` (`render: MyComponent`), not a function that renders it. For a story that needs a fixed parameter per variant (like `BreadcrumbsRouteContext`'s route), use a small factory returning a differently-closured component per story (`makeBreadcrumbsStory("category")`) rather than passing the parameter through JSX props.

### If `wp eval`-captured markup looks subtly wrong

`$_SERVER['REQUEST_URI']` is unset in a WP-CLI context, so any code with an `isset($_SERVER['REQUEST_URI']) ? ... : '<fallback>'` pattern (breadcrumbs' "is this crumb the current page" check falls back to `'/'`) behaves as if you're always on the homepage. Confirmed by reading the actual PHP, not by guessing — a `wp eval` capture is real output, but real output from a context that doesn't fully match a live request. Read the function before trusting its CLI output verbatim.

### If the `Edit`/attributes type isn't exported

Most `edit.tsx` files already export their `Edit` component (default) and `{Block}Attributes` interface (named). A block whose editor UI lives in `index.tsx` instead usually keeps both as module-local, non-exported symbols — add the `export` keyword to both and nothing else; it's a pure addition, not a refactor. If the attributes interface is generically named (`Attributes`, not `{Block}Attributes`), rename it on export to match the project's naming rule instead of leaving the generic name — it was already wrong before Storybook, this just surfaces it.

### If the block needs to be registered

`useBlockProps.save()` (used by a real `save()` component) and `ServerSideRender` (used with an `attributes` prop) both need the block registered — they call into `getBlockType(name)` internally and crash on `undefined`. Add `import "./index";` to the story file for the registration side effect. Stories that only mount `Edit` with plain `useBlockProps()` (the common case) don't need this.

## Known gotchas

- **`MediaUpload` renders nothing without the mock.** `@wordpress/block-editor`'s real `MediaUpload` export is a bare `() => null` — it's a placeholder the real editor overrides via the `editor.MediaUpload` filter at runtime. Already fixed globally in `mock-media-upload.tsx`; nothing to do per-block.
- **`ServerSideRender` always errors without a mock entry.** No live WP backend means the REST call always fails. Add a `renderXyz(attributes)` function to `BLOCK_MOCKS` in `mock-server-side-render.tsx`, returning real markup (capture it once via `wp eval 'echo render_block(...)'` against a live post, don't hand-guess the classes) — a block with no entry falls back to a plain "no mock configured yet" placeholder instead of the raw error, so it's obvious what's missing.
- **A JS animation/carousel library (Swiper, etc.) needs `createPortal(..., document.body)`, not inline rendering.** Confirmed the hard way on `banner-carousel`: every slide after the first decoded correctly (`canvas.drawImage` proved real pixel data) but never *painted* once Swiper's `transform` revealed it, specifically because the markup was nested inside the story's own `.editor-styles-wrapper`/`.kt-storybook-frame` decorator chain — moving the exact same live DOM node to `document.body` fixed it instantly, with no other change. Root cause in that ancestor chain was never pinned down further (ruled out every CSS rule found by inspection, the image files, GPU layer promotion, and React's reconciliation individually); the portal sidesteps it entirely and is also the semantically correct call for a *frontend* markup preview, which shouldn't be wrapped in an editor-canvas class to begin with. If you add a second block with real Swiper/GSAP/etc. behavior, reach for a portal from the start rather than re-deriving this.
- **Carousels need a fixed height and same-aspect-ratio mock images.** Without it, `object-fit: cover` still can't stop the box's own height from swinging between wildly different image aspect ratios per slide. Give the container an explicit height (see `STORYBOOK_CAROUSEL_HEIGHT` in `banner-carousel/save.stories.tsx`) and pick mock images of a similar aspect ratio from `mock-assets.ts`.
- **Dark/light mode toggles `<html>`, not `<body>`.** `theme-colors.scss`'s `color-scheme` rules (which `light-dark()` values in `theme.json` depend on) are scoped to `html.dark-mode`/`html.light-mode`, confirmed via a computed-`color-scheme` check — toggling only `body`'s class leaves `color-scheme` (and therefore every adaptive color) stuck. The preview decorator toggles both elements' classes now; if you add another global mode/theme toggle, check which element the real site's CSS actually targets before assuming `body`.
- **A small logo/icon image blurs badly once stretched into a full-size card or carousel slide.** Use a real photo from `mock-assets.ts` sized for the context, not whatever's smallest/first to hand.
- **A story's `render` must be the function Storybook itself invokes, not a wrapper that renders a hook-using child via JSX.** `useArgs()`/`useInteractiveAttributes()` throw `hooks can only be called inside decorators and story functions` otherwise. See "If the story's `render` needs a Storybook hook" above.
- **A block's own `style.scss` doesn't come along for free.** It's only ever imported by that block's own `index.ts`/`init.ts` webpack entry (not any global bundle) — a story that doesn't also `import "./style.scss";` renders correct markup with zero of the block's own CSS.
- **`storybook-static` must stay out of ESLint.** It's a 70+ MB directory of minified bundles; without an `.eslintignore` entry, `lint:js` doesn't error, it just hangs (confirmed: 20+ minutes, still running, no output). Already added — if `npm run lint:js` seems to hang, check this hasn't regressed first before assuming a real bug.
- **A block's dropdown stuck on "Loading…" isn't a bug.** `content-block` and `navigation` query `core`'s real `getEntityRecords()` selector (for reusable blocks / `wp_navigation` posts) with no live WP backend to resolve it — same category of gap as `InnerBlocks` below, just for a `SelectControl` instead of child blocks. Wire the rest of the block's Controls to `useInteractiveAttributes()` anyway and say so in `parameters.docs.description.component`.
- **A block built on `InnerBlocks` renders empty in Storybook, with no error to chase.** `content-tabs` mounts real `<InnerBlocks>`, which silently no-ops without a full `BlockEditorProvider` block-tree context — Storybook throws nothing, logs nothing, the nav/panel wrapper divs just stay empty. Unlike `ServerSideRender` (fixable with a `BLOCK_MOCKS` entry), there's no lightweight mock for a real nested block tree; wire the block's own `InspectorControls`-driven attributes to `useInteractiveAttributes()` anyway (the outer wrapper's classes/styles do still respond) and document the gap in the story's `parameters.docs.description.component` rather than chasing a fix.
- **A frontend script's `document.addEventListener("DOMContentLoaded", ...)` never fires in Storybook.** Storybook's page has already finished loading by the time a story imports the script, so a top-level `DOMContentLoaded` listener (no immediate-run fallback) silently never attaches — this is why `gallery-lightbox`'s lightbox and `modal-trigger`'s open/close both looked "broken" in Storybook despite working fine on the real site. Fix at the source, not in the story: export an `init...()` function and guard it with `if (document.readyState === "loading") { document.addEventListener("DOMContentLoaded", init); } else { init(); }` (the exact pattern `gallery-lightbox/init.ts` already had and `modal-manager.ts` was retrofitted to match) — a pure, non-breaking addition since real WP page loads always hit the `"loading"` branch unchanged.
- **`InspectorControls` panels rendered into an empty sidebar for every existing story — root cause found and fixed.** Calling a block's `Edit` function directly (the pattern used by nearly every story before this fix) skips `@wordpress/block-editor`'s real `<BlockEdit>` dispatcher entirely. `InspectorControls`' `Fill` (`block-editor/src/components/inspector-controls/fill.js`) reads `useBlockEditContext()[mayDisplayControlsKey]` and returns `null` if it's falsy — and that key is a module-private `Symbol` only ever set by `<BlockEdit>` itself (via `<BlockEditContextProvider value={{ ..., [mayDisplayControlsKey]: mayDisplayControls }}>`), which no story ever rendered. Fix: `RealBlockEdit` (`@utils/storybook-edit-props.ts`) renders the block through the actual `BlockEdit` component (imported via `import * as blockEditor from "@wordpress/block-editor"`, cast — it's a real, public, un-prefixed export but untyped in `@types/wordpress__block-editor`), passing `isSelected: true` and `mayDisplayControls: true` explicitly. This also means the block's real `editor.BlockEdit` filters now actually fire — no more manually re-applying a HOC by hand the way the first `modal-trigger` attempt did.
  - **Usage:** `<RealBlockEdit name="kotlinskidev/x" attributes={attributes} setAttributes={setAttributes} />` in place of `<Edit attributes={...} setAttributes={...} />`. Requires the block registered (`import "./index"` — same requirement as `ServerSideRender`-with-attributes or real `save()`).
  - **Gotcha inside a gotcha:** fixing this exposed a *second*, block-specific bug in `breadcrumbs/index.ts` — it called `registerBlockType(metadata.name, { edit: Edit })` (name string only) instead of `registerBlockType(metadata, { edit: Edit })` (full object, the convention every other block in this repo follows). The real WP admin never noticed because PHP's `register_block_type()` bootstraps the block's attributes/supports server-side before any JS runs; Storybook has no such bootstrap, so `getBlockType()` returned a type with no `attributes`/`supports`/`apiVersion` and `<BlockEdit>` silently rendered nothing, no console error at all. Fixed by passing full `metadata`. If a block goes through `RealBlockEdit` and renders blank with zero console output, check this first.
  - **Not yet retrofitted:** only `modal-trigger` and `breadcrumbs` use `RealBlockEdit` so far. Every other block's story still calls `Edit` directly, meaning their `InspectorControls` content is still unverified/likely invisible the same way — same fix applies, not yet applied everywhere.
- **A block with no story might share its `Edit` with siblings in one unexported module.** `nav-banner`/`nav-image`/`nav-link`/`nav-paragraph` all pointed their `block.json`'s `editorScript` at the same `nav-content/index.tsx`, which registered all 4 block types but never exported the individual `Edit` functions or attribute interfaces — nothing to import from each block's own folder. Fix is the same as step 1's normal case, just at a different file: add `export` to each `{X}Edit` function and `{X}Attributes` interface in the shared module, then story each block from its own folder (`import { XEdit, type XAttributes } from "../shared-folder"`). Separately, some `nav-*` blocks (`nav-language-panel`, `nav-popular-pages`, `nav-search-panel`) register the *exact same* `Edit` as a non-`nav-` sibling block under a second block name for a different insertion context — those need no story of their own at all; check `registerBlockType` calls in the sibling's `index.tsx` before assuming a missing story is a real gap.
- **Links turned fully invisible on `:hover` in Storybook only, never on the real site.** The sitewide `global.scss` hover rule renders link text via `background-clip: text` + `-webkit-text-fill-color: transparent` against `--kt-text-gradient`, which resolves to `--wp--preset--gradient--fancy-text-{dark,light}`. `wp-preset-tokens.ts` only replicated color/spacing/font-size tokens, not gradients, so that custom property was empty in Storybook — confirmed by comparing `getComputedStyle` between a live hover on the real site (gradient renders) and the same hover in Storybook (empty value) rather than assuming. Any new `theme.json` preset category (durations, shadows, etc.) used via `var(--wp--preset--*)` needs the same treatment in `wp-preset-tokens.ts` before trusting a "looks wrong in Storybook" report as a real bug.

## Adding a new block's story, step by step

1. Check whether `Edit`/the attributes interface (or `Edit`+attributes for an `index.tsx`-only block) are exported. Add `export` if not (see above).
2. Create `edit.stories.tsx` (or `index.stories.tsx`/`save.stories.tsx`) next to the source file.
3. Import `getDefaultAttributes` (and `useInteractiveAttributes`, `buildEditProps` if the block's `Edit` is typed against the full `BlockEditProps<T>` rather than a narrow local props type — check the block's own prop type first) from `@utils/storybook-edit-props`.
4. Write a small `XyzStory()` component using `useInteractiveAttributes<XAttributes>()`, and set the component itself (not a wrapper that renders it via JSX) as the story's `render`.
5. `export const Default: Story = { args: { attributes: getDefaultAttributes<XAttributes>(metadata.attributes) } }`.
6. If the block has its own `style.scss`, add `import "./style.scss";` to the story — it isn't pulled in by any global stylesheet.
7. If the block uses `ServerSideRender` with an `attributes` prop, or a real `save()`/`useBlockProps.save()`, add `import "./index";` for block registration.
8. If the block's preview is completely empty with `ServerSideRender`, add a `BLOCK_MOCKS` entry in `mock-server-side-render.tsx` using real captured markup — read the PHP behind it first if anything in the capture looks state-dependent (see "If `wp eval`-captured markup looks subtly wrong" above).
9. Build (`npx storybook build`) and check the story renders with zero console errors — a static build succeeding is not sufficient proof by itself; use a headless-browser check (Playwright is already a devDependency) against the *built* `storybook-static/` output, not just the dev server, since dev-only warnings can hide real build-time breakage and vice versa.

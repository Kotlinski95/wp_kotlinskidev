# Server 522 error

## Connection timed out — Error code 522

From time to time, receiving a 522 error on kotlinskidev.com. Happened before (months ago) and again 2026-07-28 → 2026-07-30.

## Hosting

Site is hosted on an AWS EC2 instance, DNS/CDN via Cloudflare (kotlinskidev.com, proxied).

## What a 522 actually means

Cloudflare error 522 = "Connection timed out." Cloudflare's edge reached the browser fine and the Cloudflare network is healthy, but Cloudflare could **not open a TCP connection to the origin server** within its timeout window. It is an origin-side failure — not a DNS problem, not a Cloudflare outage.

## Incident: 2026-07-28 22:20 UTC → 2026-07-30

- Instance: `i-036f11488611a435b` (kotlinskidev), Ubuntu 24.04 LTS, no Elastic IP attached (public IP `56.228.24.75` at the time).
- EC2 **instance status check** began failing at `2026-07-28T22:20:00Z` ("impaired"). **System status check stayed OK** the entire time — the underlying AWS host/hardware was fine, but the guest OS on the instance stopped responding to all network traffic, including SSH, for ~40 hours.

## Diagnostic steps (in order)

1. **Confirm it's actually a 522, and where the failure sits**

   ```bash
   curl -sS -o /dev/null -w "HTTP %{http_code}, connect %{time_connect}s, total %{time_total}s\n" https://kotlinskidev.com/
   ```

   Result: `HTTP 522`, connect time ~0.02s (fast — reached Cloudflare fine), total time ~19s (Cloudflare's own origin-connect timeout). Fast connect + eventual 522 = Cloudflare is healthy, origin is the problem.

2. **Rule out DNS / Cloudflare-side issues**

   ```bash
   dig +short kotlinskidev.com A
   dig +short kotlinskidev.com NS
   ```

   Resolved fine to Cloudflare anycast IPs (`188.114.x.x`) via `annabel.ns.cloudflare.com` / `mitchell.ns.cloudflare.com`. DNS and Cloudflare's network ruled out.

3. **Check the origin at the AWS level (EC2 console)**
   - Instance state: `Running`
   - Status checks: **2/3 passed** — "Instance reachability check failed", "System status: ok"
   - This is the critical signal: hypervisor/hardware fine, **guest OS unresponsive**.

4. **Attempt EC2 Instance Connect (browser-based SSH)**
   - Failed: "Failed to connect to your instance. Error establishing SSH connection." Expected — EIC needs a live OS network stack to deliver the temporary key, and the OS wasn't responding to anything.
   - Security group, NACL, and route table were all confirmed correctly configured (port 22 open, default route via IGW active) — ruled out as the cause. (The console's "port 22 open to 0.0.0.0/0" warning is a hardening suggestion, unrelated to this outage.)

5. **Check for an Elastic IP before doing anything that power-cycles the instance**
   - None found (`EC2 → Network & Security → Elastic IPs` was empty). Matters because a full **Stop → Start** (unlike Reboot) reassigns a new public IP unless an EIP is attached — which would also require updating the Cloudflare DNS A record afterward.

6. **Recovery attempt: Reboot instance** (EC2 console → Instance State → Reboot)
   - Non-destructive, keeps the public IP regardless of EIP status. Tried first, before the more disruptive Stop/Start.
   - **Result: fixed it.** Status checks went to 3/3 passed, site came back online.

   (Had this not worked, next step would have been Stop → Start, accepting a new public IP and updating the Cloudflare A record, then EC2 Serial Console if it still failed to boot, to see kernel panic/fsck output.)

## Root cause

Not fully confirmed at the time of the incident (journald logging was volatile, not persistent, so the pre-reboot kernel log was lost — see Part 7 of `docs/monitoring.md`, now fixed for next time). But the signature (Running + system-status-ok + instance-reachability-failed + fixed by a plain reboot, no host migration needed) points at a **guest-OS-level hang, not a hardware fault**.

**Refined theory (2026-07-30, after inspecting the live server via `free -h` / `ps aux`):** the original "no swap configured" hypothesis was wrong — 4GiB of swap was already present (a CloudPanel default) and already ~18% in use at a fairly idle moment. Combined with the fact that this ~914MiB instance runs **10 concurrent PHP-FPM version stacks** (CloudPanel installs 7.1 through 8.4 plus its own default pool, though only one is used by the site) alongside MySQL, nginx, and the OS, the more likely mechanism is **swap thrashing under load** — memory pressure severe enough to slow the guest OS past Cloudflare's connect timeout, without necessarily triggering a clean OOM-kill. Full setup for confirming this (persistent kernel logs, swap/memory alarms) and the fix (disabling unused PHP-FPM versions, right-sizing `pm.max_children`) is in `docs/monitoring.md`.

Other possibilities, still worth ruling out via the follow-up checklist below:

- **Root volume filled up** — logs, DB growth, or backups filled the disk, and the OS hung trying to write (journal, MySQL binlogs, WP uploads).
- **A stuck process** (e.g. an unattended kernel/system upgrade, a runaway cron job) pinning CPU/I/O hard enough to kill network responsiveness.

## Follow-up to actually confirm root cause (do this once back online)

- [ ] `dmesg -T | grep -iE "oom|killed process"` and `sudo journalctl -k -b -1` — look for OOM-killer or kernel panic messages around 2026-07-28 22:20 UTC.
- [ ] `df -h` and `free -h` — check current disk headroom and whether swap exists.
- [ ] Check CloudWatch `CPUUtilization` (and memory, if the CloudWatch agent is installed) around the failure window for a spike-then-flatline pattern.
- [ ] `sudo journalctl -u nginx -u php*-fpm -u mysql --since "2026-07-28 22:00" --until "2026-07-29 00:00"` for service-level clues right before the hang.

## Prevention

Full step-by-step setup (alarms, CloudWatch agent, swap/log status, PHP-FPM cleanup) lives in **`docs/monitoring.md`**. Summary:

- [ ] **Allocate and attach an Elastic IP** to this instance, so a future Stop/Start doesn't also require a Cloudflare DNS update mid-incident.
- [ ] Add CloudWatch alarms on `StatusCheckFailed_System` (Recover action) and `StatusCheckFailed_Instance` (Reboot action), so future guest-OS hangs self-heal instead of causing multi-hour outages.
- [x] Swap — already present (4GiB, CloudPanel default), confirmed 2026-07-30.
- [ ] **Disable the 9 unused PHP-FPM version stacks** (only one is actually needed) and right-size `pm.max_children` for the ~914MiB instance — the highest-leverage fix given the confirmed memory pressure.
- [ ] If root cause turns out to be disk: add a disk-usage CloudWatch alarm plus log rotation/cleanup (backups, debug logs, binlogs).
- [ ] Install the CloudWatch agent — default EC2 metrics don't include memory or disk usage, which are exactly what's needed to catch this before it becomes a 522.

## Fast recovery checklist (for the next 522)

1. `curl -sS -o /dev/null -w "HTTP %{http_code}, connect %{time_connect}s\n" https://kotlinskidev.com/` — confirm 522, check connect time (fast connect = Cloudflare fine, origin is the problem).
2. `dig +short kotlinskidev.com A` / `NS` — confirm DNS/Cloudflare isn't the cause.
3. AWS EC2 console → instance state + status checks. Note which check failed (System vs Instance).
4. If "Instance reachability check failed" + "System status: ok" → guest OS hang. Try **Reboot** first (keeps public IP either way).
5. Wait ~5 min, recheck status checks.
6. If still impaired: check for an Elastic IP, then **Stop → Start** (update the Cloudflare A record afterward if no EIP is attached).
7. If it still won't come back: EC2 **Serial Console** for boot-time diagnostics (kernel panic / fsck stuck at boot).
8. Once back up: pull `dmesg` / `journalctl` logs from the failure window before closing out the incident, so root cause gets fixed and not just papered over.

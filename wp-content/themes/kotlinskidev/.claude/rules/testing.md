## JS/TS Unit (Jest)
- Config file must be named exactly `jest-unit.config.js` — `wp-scripts test-unit-js` looks for that filename specifically; `jest.config.js` is silently ignored.
- Re-spread `@wordpress/scripts/config/jest-unit.config.js` in the project config rather than replacing it — Jest project config overrides, it does not merge.
- Use `@testing-library/react` + `@testing-library/user-event` for components, `@testing-library/jest-dom` for matchers.
- If a component only *imports* a heavy/ESM-only `@wordpress/*` dependency but never renders it on any tested path, mock the whole module (`jest.mock(...)`) instead of fighting `transformIgnorePatterns`.
- `transformIgnorePatterns` exceptions need a leading `.*` (`node_modules/(?!.*(uuid)/)`) to catch the package when it's nested deeper than the first `node_modules/` segment.
- If a module under test registers a listener on `document`/`window` (not a local element) at load time, `jest.resetModules()` + `require(...)` in each test creates a *new* listener without removing the old one — stale listeners from earlier tests keep firing on later tests' events, double-invoking handlers with mismatched mock state. Track listeners via `jest.spyOn(document, "addEventListener").mockImplementation(...)` in the top-level `beforeEach` and `removeEventListener` them all in `afterEach` (see `protected-content.test.ts`).

## PHP Unit (Pest + Brain Monkey)
- Extend `Tests\TestCase` — it wires Brain Monkey's `setUp()`/`tearDown()`.
- Never add real `add_action`/`add_filter` calls inside a unit test file scope — this project's convention fires those at `require` time, before Brain Monkey mocking is active; `tests/Pest.php` already stubs them.
- Coverage must run as `php -d pcov.directory=. vendor/bin/pest --coverage` — `pcov.directory` is `INI_SYSTEM`-scoped and cannot be set via `phpunit.xml`; unset, it silently excludes `functions/`/`includes/`.

## PHP Integration (Pest + wp-phpunit + WP_UnitTestCase)
- Runs today via `composer test:integration` (`tests/integration/` has its own `composer.json`/vendor, isolated from the theme's root `vendor/`) — no Docker needed, no `wp-env`. Do not re-litigate an old "blocked, needs Docker" note without first running the command yourself; that constraint no longer applies.
- New test files go in `tests/integration/tests/`, one file per `functions/*.php`/`includes/*.php` module, named `{StudlyModuleName}Test.php`. Start with `uses(Tests\Integration\TestCase::class);`, then plain Pest `it(...)`/`expect(...)` — no class wrapper needed.
- Prefer exercising a `render_block` filter through the real pipeline (`render_block(parse_blocks($comment))`) over calling the filter function directly — confirms the filter is actually registered on the hook, not just that the function works in isolation, and matches real serialized block-comment input. Call the bare function directly only for a helper that isn't itself a hook callback (e.g. a pure predicate like `kotlinskidev_is_current_link_url()`).
- **`update_option($key, false)` silently no-ops if the option doesn't already exist** — WordPress core treats `false` as its own internal "this option doesn't exist" sentinel, so `update_option()`'s old-vs-new comparison sees no real change and never persists the row; `get_option($key, true)` then still returns the `true` default, not `false`. Confirmed by direct check, not assumed. Use `add_option($key, false)` instead when a test needs to set a boolean-`false` option value from a clean (nonexistent) state.
- Never `unset($_SERVER['REQUEST_URI'])` in a test's cleanup — several WP core code paths (e.g. `_wp_cron()`) read it unconditionally and throw on a genuinely missing key. Save the original value in `beforeEach` and restore it in `afterEach` instead.
- A function-local `static` cache (or a `define()`d constant used for feature detection) persists for the **entire test run**, not per-test — Pest/PHPUnit runs every test in one shared PHP process by default. Whichever test calls it first, in any file, permanently locks in that result for every later test. Don't try to test the dynamic/override behavior of code like this; test only the safely order-independent parts (pure functions, the guaranteed-default-state path) and document the gap rather than reaching for `@runInSeparateProcess` or a source change mid-coverage-pass.
- Never call a function that ends in `wp_send_json_*()`/`wp_die()`/a bare `exit()` directly unless the test class is `WP_Ajax_UnitTestCase` (this project's `Tests\Integration\TestCase` is plain `WP_UnitTestCase` and does **not** install the exception-throwing die handler) — confirmed once, safely, in a throwaway probe: it silently kills the whole `pest` process mid-run with no test summary at all. Test only the early-return branches of a function shaped like this; the branch that actually dies is untestable under the current base class.
- `wp_scripts()`/`wp_styles()` registrations (and other non-DB global registries) are **not** covered by WP_UnitTestCase's per-test transaction rollback — only real DB writes are. A test asserting against one specific script handle can pass every time run alone and fail only in the full suite, because an earlier file already registered that exact handle for real. Always run the full suite once (`composer test:integration`, no filter) before calling a new integration test done, not just the new file filtered — this class of bug is invisible any other way.
- Before writing a test for a `functions/*.php`/`includes/*.php` file, confirm its `require_once` in `functions.php` isn't commented out. A file can have a real, correctly-written hook registration and still be completely dead on the live site — grep `functions.php` for the file's own require line before assuming it's loaded; don't fabricate coverage for code that never actually runs.

## E2E (Playwright) — Setup
- Run via `npm run test:e2e` (`wp-scripts test-playwright`). Never use `test-e2e` — that's a separate, older Puppeteer-based script in the same package.
- Targets the real running LocalWP site, not `wp-env`. Never change `playwright.config.js`'s `baseURL` logic to assume `wp-env` without checking Docker is actually available.
- Never drop or change `locale: "pl-PL"` in `playwright.config.js` without checking Polylang redirect behavior — it's forwarded as `Accept-Language` and drives auto-redirect.
- Never lower the desktop viewport below `1280×800` — `@wordpress/scripts`' own default (960×700) falls inside the tablet range and changes which nav markup renders.
- Every `test.beforeEach` must call `acceptCookies(page)` (from `tests/e2e/utils.ts`) before interacting with anything else — the Complianz banner intercepts pointer events on first load otherwise.

## E2E — Content-Agnostic Selectors (mandatory, not optional)
- Never select elements by visible text, menu labels, or link text (`getByRole("link", { name: "..." })` with a literal string). WP admin content — menu items, labels, page slugs — changes routinely and independently of the behavior under test.
- Select by structural, code-owned attributes instead: CSS classes defined in `render.php`/block templates, `data-panel`, `aria-controls`, `aria-current`, `aria-expanded`, `role`, `rel="home"`, input `type`.
- Never assert a hardcoded destination URL. Read the target link's `href` at runtime and assert the resulting page against *that* (via `clickAndExpectNavigation()` in `tests/e2e/utils.ts`, which also trailing-slash-normalizes — a relative `href` and WP's canonical URL are the same destination).
- Always exclude same-page/disabled links from generic "pick any live link" locators — use `getFirstLiveLink()` / the `NOT_CURRENT_PAGE` selector fragment from `tests/e2e/utils.ts`. This theme makes links to the current page `aria-disabled`/`kt-link-current` by design; a naive `.first()` pick can land on one and hang.
- Never click through external/third-party links (social icons, etc.). Assert they look like a real external link (`href` matches `^https?:\/\//`) and stop there.
- When a test depends on current content having a specific *shape* (e.g. a menu branch nested 3 levels deep, ≥2 siblings to test accordion collapse) rather than just *existing*, search live content for a qualifying example and `test.skip()` with a clear reason if none currently qualifies. Never hardcode which specific item is assumed to have that shape.
- Do not add this exists-then-skip pattern for template-level structure (a block being present in `parts/*.html` at all) — if a whole block/section is missing, that's a real regression the test should fail on, not skip past.
- Exception, not a contradiction: content-agnosticism applies to *externally-editable* content you don't control (real menu items, real pages). A fixture the test itself created (a WP-CLI-seeded page, block markup set via `editor.setContent()`) is fully test-controlled — asserting an exact value against it is correct and expected, not a violation of this section.

## E2E — Block-Level Testing (Frontend + Editor)
- Before writing anything, check whether the target is actually a standalone block (`block.json` + `render.php` in `src/blocks/<name>/`) or a filter-based extension of existing core blocks (`blocks.registerBlockType`/`editor.BlockEdit`/`blocks.getSaveContent.extraProps` in a plain `index.tsx`, no `block.json`). The theme's own README block table lists both kinds the same way — don't assume from the table, look at the directory.
- Use `@wordpress/e2e-test-utils-playwright`'s `Admin`/`Editor`/`PageUtils` (already present — transitive dependency of `@wordpress/scripts`, confirm with `npm ls @wordpress/e2e-test-utils-playwright` before assuming it needs installing). Construct manually (`new Editor({ page })`, `new Admin({ page, pageUtils, editor })`) inside a normal `@playwright/test` spec using this project's `storageState` auth — do not use the package's own fixture-wired `test` export or `requestUtils`, which authenticate via REST API Basic Auth, a different mechanism than this project's cookie-based session.
- Prefer `editor.insertBlock({ name, attributes })` over driving the block-inserter UI, and `editor.getEditedPostContent()` to assert on the real serialized block markup a filter produced — both far more deterministic than reading rendered DOM state.
- A block's canvas wrapper has `role="document"` with a name like `"Block: Heading 2"`, not `role="heading"` — the `edit()` canvas and `save()`/frontend output are separate render trees; roles correct for one do not apply to the other.
- Never give a fixture/post a title that shares words with something you're about to locate by role+name in the same test — the editor's own document-bar breadcrumb button's accessible name is the post title, and will collide with e.g. `getByRole("button", { name: /Feature Name/ })` if the post is titled with that same feature name.
- When testing "panel absent for an unsupported block," pick a block with no inner blocks (e.g. `core/separator`). A wrapper block (`core/quote` etc.) can auto-select an inner block on insert, and if that inner block type is itself supported, the sidebar reflects the inner block, not the wrapper — a false failure, not a real one.
- For WP-CLI-backed test fixtures (real pages/content a frontend spec needs to exist): use `execFileSync("wp", [...argsArray])`, never `execSync` with an interpolated shell string — avoids all shell-escaping concerns for arbitrary block HTML content. Pass `stdio: ["ignore", "pipe", "ignore"]` — the default inherits stderr, which leaks unrelated PHP deprecation-notice noise from other plugins into every test run. Use `wp post get <id> --field=url`, not `wp post list --include=<id>` — `--include` does not filter the way it looks like it should.
- Always verify fixture cleanup actually happened (`wp post list --name=<slug> --field=ID` empty afterward) rather than assuming `test.afterAll` ran correctly.
- `admin.createNewPost()` creates a real `auto-draft` post row every call, even without saving — normal WordPress behavior (same as a human opening "Add New Page"). WP-Cron only reaps these after 7 days, which is far slower than this suite accumulates them during active development — a single day of iteration produced 400+ orphaned rows in practice, confirmed by direct DB audit, not a theoretical concern. Don't build per-spec cleanup for this (still no need to capture/delete the draft ID in each of the 8 `tests/e2e/editor/*.spec.ts` files) — `npm run test:e2e` runs `npm run test:e2e:purge-drafts` unconditionally afterward (chained via `; e=$?; ...; exit $e` in `test:e2e`'s own script, not npm's automatic `post`-script hook, which does **not** fire when the main script exits non-zero — confirmed empirically, not assumed).
- `reducedMotion` is genuinely honored via this project's `use.contextOptions.reducedMotion` (not the more common top-level `use.reducedMotion`) — confirm with a throwaway probe before trusting either the default or an override, in both directions. The default suite runs with reduced motion **on**, so any animation-driven block needs an explicit `test.use({ contextOptions: { reducedMotion: "no-preference" } })` block to exercise the real animating code path at all — otherwise you're only ever testing the instant-final-value branch.
- For a **static block** (`save()`-based, HTML baked into `post_content`, no `render.php`), a hand-authored frontend fixture must include the real `<!-- wp:namespace/name {attrs} -->` ... `<!-- /wp:namespace/name -->` block comment wrapper around the markup, not just the resulting HTML. WordPress's automatic `viewScript` enqueueing detects a block's presence by parsing the block comment, not by scanning rendered HTML for the block's CSS classes — omit the comment and the frontend script silently never loads, with no error, just a non-functional block. The comment's own JSON attribute blob is plain `JSON.stringify(...)`, no HTML-entity escaping — it's inside a comment, not a tag attribute; only a real `data-*="..."` tag attribute needs `&quot;`-escaped quotes.
- `RangeControl` renders **two** inputs sharing one `aria-label` — a `role="slider"` and a `role="spinbutton"`. Plain `getByLabel(...)` is ambiguous (Playwright strict-mode error) for any `RangeControl`-backed setting. Scope to `getByRole("spinbutton", { name })` when filling an exact value.
- Prefer regex-based/attribute-string assertions (`content.toContain('"attr":true')`) over hand-replicating exact core-block markup in fixtures when the server-side logic under test is itself structurally naive (e.g. a `render_block` filter that regexes for `<img...>`/`<video...>` substrings) — confirm the filter's actual matching mechanism first; if it's not structure-sensitive, a fixture doesn't need to be either.
- Some core blocks (`core/image`, `core/cover`, ...) split their Inspector into a default "content" view and a separate **"Settings" sub-tab** — a plain `<InspectorControls>` call (no `group` prop) only renders once that sub-tab is active. Others (`core/heading`, this theme's own custom blocks so far) have no such split. Always call `openBlockSettingsTab(page)` (from `tests/e2e/utils.ts`) after selecting a block and before looking for a custom panel — it's a no-op when the block has no such tab, so it's safe unconditionally.
- Clicking a `core/cover` block's content area in the canvas selects its **inner placeholder block** (a paragraph), not the Cover block itself — it always has an inner block. Click the block toolbar's own breadcrumb button (`page.getByRole("button", { name: "Cover", exact: true })`) immediately after to select the actual parent, rather than hunting for a click target that avoids the inner block.
- Before asserting a click-driven interaction (a backdrop-click-to-close, an outside-click-to-dismiss), verify the target element is actually reachable by a real click at a real viewport size — a full-bleed child (`flex: 1; width: 100%` inside a single-flex-item parent) can cover 100% of a parent's clickable area with zero exposed gap, making an `e.target === parent` check in the source unreachable in practice regardless of what the code says. Confirm with `document.elementFromPoint(x, y)` at the target area's edges/corners in a throwaway probe before writing the test; if nothing ever resolves to the intended target, don't write a test pretending a user can reach it — remove or skip it with a reason instead.
- An `InspectorControls` panel can be conditional on **block content**, not just block type (e.g. a "Video Options" panel that only appears when `images.some(item => item.type === "video")`) — the same "panel absent/present" testing pattern used for unsupported-block-type cases applies here too: insert the same block twice with different attribute values and assert the panel's presence directly, rather than assuming any panel maps 1:1 to a block name.
- A wrapper `<div>`/class around a toggle-revealed control can be present **unconditionally**, even before the toggle is on — don't assume a CSS class you see in source is itself the "revealed" signal. Confirm which specific element only exists after the toggle fires (usually the actual new control, e.g. a second `MediaUpload` button) before asserting a before/after count on it.
- `getEditedPostContent()` never includes an attribute still equal to its `block.json` default — WordPress's own serializer omits it entirely. Only assert a `"key":"value"` substring for an attribute the test actually changed away from its default.
- For a fully dynamic block (`save: () => null`, `render.php`-only), a hand-authored frontend fixture can use the compact self-closing block-comment form (`<!-- wp:name {attrs} /-->`, no inner HTML) — `render_block()` calls `render.php` with `$attributes` only and ignores the block's saved inner content entirely.
- Same applies to a `render_block` filter that derives its own output purely from `$block['attrs']`, not from `$block_content` — a hand-authored fixture doesn't need any of the classes/markup the filter itself would add present already; confirm with a probe that the filter really is attribute-only before relying on this.
- For a block whose `save()` emits `<InnerBlocks.Content />` (real children, not `null`) **but** whose `block.json` still declares a `render` override (e.g. `kotlinskidev/scroll-section`), a hand-authored fixture must contain *only* the child block comments — never a hand-typed copy of the wrapper markup `render.php` itself builds. `render_block()` assembles `$content` from the block's own saved `innerContent` (including any wrapper you hand-typed) before handing it to `render.php`, which then wraps that in a *fresh* wrapper of its own — nesting a duplicate. Symptom: `page.locator(".the-wrapper-class")` resolves to 2 elements instead of 1. Verify actual rendered HTML with `curl` + `grep -o` against a throwaway `wp post create` page when a locator count looks doubled, rather than assuming the fixture markup itself is correct.
- A set of repeated per-device/per-breakpoint control panels (Desktop/Tablet/Mobile, etc.) sharing identical control labels with no `fieldset`/`aria-labelledby` grouping makes `getByRole(..., { name })` alone ambiguous across all of them. If each panel's own heading is a direct sibling of its controls in one wrapper `<div>` (confirm via probe), scope with `page.getByRole("heading", { name, level }).locator("xpath=..")` and chain further `getByRole()` calls off that.
- Before writing a test, check whether the code path is actually reachable at all — a `render_block`/filter branch keyed on an attribute or option that nothing in the codebase ever sets is a permanent no-op, the same "don't test unreachable code" judgment already made for a CSS-covered click target, just via a different root cause (grep the whole `src/`/`functions/`/`includes/` tree for the attribute name before assuming a branch is live).
- A `render_block` PHP filter that merges classes into an existing `class` attribute is typically additive-only — it can't undo a wrong/stale class a client-side `blocks.getSaveContent.extraProps` filter already baked into the saved static HTML. If JS and PHP use different equality semantics against the same attribute (JS strict `!==` vs PHP loose `!=`), the PHP side's more-correct logic still can't fix output the JS side already got wrong at save time.
- Before assuming an Inspector panel is broken because its enqueued script errors in the console, check whether the same source file is *also* imported into a different, correctly-bundled webpack entry (e.g. a shared `editor.ts`) — a redundant broken enqueue and a genuinely working feature can coexist. Verify the panel actually renders/functions before concluding otherwise.

## E2E — Authenticated / Site Editor Tests
- Testing must happen *inside* the Playwright suite, never by manually driving a logged-in browser session yourself to explore or "verify" the editor. If you need to see real editor DOM/behavior before writing a selector, write a throwaway authenticated Node+Playwright probe script (same discipline as the frontend content-agnostic rules above), run it, read its output, then delete it — don't substitute your own interactive browsing for that.
- The real login URL is `/login/`, never `/wp-login.php` or `/wp-admin` directly — this site's `whl_redirect_admin` option 404s those. If the login path is ever in doubt, confirm it via `wp option get whl_page` (WP-CLI), don't guess.
- A login-attempt limiter is active (lockout after repeated failures). Never iterate/guess against the real login form — verify field selectors read-only first (navigate + inspect, no submit) before ever submitting real credentials.
- Test credentials live only in `tests/e2e/.env` (gitignored — confirm with `git check-ignore -v` before trusting any new secret file, don't assume a name matches an existing glob). Never hardcode a username/password inline in a spec file or in `global-setup.js`. `tests/e2e/.env.example` (committed) documents the required keys with empty values.
- `playwright.config.js`'s `globalSetup` (`tests/e2e/global-setup.js`) must no-op with a warning, not throw, when credentials are absent — it must never break the anonymous frontend suite for people/environments without admin access configured.
- Editor/authenticated spec files live under `tests/e2e/editor/` and must opt in to the saved session explicitly per-file via `test.use({ storageState: path.join(process.env.WP_ARTIFACTS_PATH ?? ..., ".auth", "admin.json") })`. Never set `storageState` globally in `playwright.config.js`'s shared `use` block — that would silently authenticate the frontend specs too, which must stay anonymous (see the page-cache-divergence rule below).
- After changing `global-setup.js` or the login flow, verify through the real runner (`npx wp-scripts test-playwright tests/e2e/editor/...`), not just a standalone Node script — `wp-scripts` must actually pick up `globalSetup` from the config, and a standalone script bypasses that check.

## E2E — Viewport / Responsive
- Split viewport-dependent tests into a nested `test.describe` with `test.use({ viewport })` scoped to that block, inside the same spec file — never a separate spec file per breakpoint, never a second Playwright `project` that re-runs the whole suite at every size.
- Mobile viewport: `390×844` (confirmed under this theme's `$breakpoint-mobile: 782px`). Add a `tablet viewport` block only if a test actually needs tablet-specific markup.

## E2E — Known Gotchas
- `hamburger.locator(A).locator(':scope > B:has(...)')` — splitting a selector across two chained `.locator()` calls silently matches nothing when the *second* call's fragment contains `:has()`. Build multi-level selectors as one fully self-contained string instead (see `TOP_ITEM_EXPANDED`/`NESTED_ITEM_EXPANDED` in `header.spec.ts`).
- Never verify selectors by inspecting an authenticated wp-admin browser tab — logged-in sessions bypass this site's page cache, and the markup an admin sees can differ from what an anonymous visitor (and Playwright, which is always anonymous) actually gets. Verify against a real Playwright run.
- For an element hidden via ancestor `overflow: hidden` + `max-height: 0` (an animated accordion collapse, not `display: none`): a bounding-box/visibility check on the *descendant* is unreliable — ancestor clipping doesn't shrink a child's own layout box. Assert on the real state attribute (`aria-expanded`) instead, and trust Playwright's click-actionability for "can this actually be reached."
- For an element hidden via `transform: translateY(...)` (an off-screen slide, not `display: none`): `toBeVisible()`/`toBeHidden()` won't catch it — it still has a layout box. Assert on `getBoundingClientRect().top` or the toggled CSS class instead.
- Set scroll position with `page.evaluate(() => window.scrollTo(x, y))`, not `page.mouse.wheel()` — wheel-simulated scrolling interacting with smooth-scroll behavior produced inconsistent final state in practice.
- Put shared spec helpers in `tests/e2e/utils.ts`, not duplicated per spec file. Add to it rather than reimplementing `acceptCookies`/`clickAndExpectNavigation`/`normalizePath`/`NOT_CURRENT_PAGE`/`getFirstLiveLink` locally.
- `.filter({ hasText })` matches **any ancestor** whose text content includes the target text, not just the element that directly contains it — a selector like `page.locator(".wp-block-group").filter({ hasText: "Item C" })` in a fixture with nested groups can resolve to the page's own `<main>` landmark plus every enclosing wrapper, a Playwright strict-mode error, not a real ambiguity in the fixture. Give the specific element its own marker class in the fixture instead of relying on `hasText` to disambiguate structure you control.

## Hooks
- `test:e2e` and `test:php:integration` are deliberately not wired into `.husky/pre-push` (they need a live site / Docker respectively) — do not add them to the hook. Run manually before merging anything touching navigation, language switching, theme toggling, the floating header, or deferred block asset registration.

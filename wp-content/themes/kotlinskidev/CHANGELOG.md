# Changelog

All notable changes to the kotlinskidev theme are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this theme follows [Semantic Versioning](https://semver.org/):

- **MAJOR** — breaking change: removed/renamed a block or attribute, a template/pattern change that requires editors to re-save affected content, a markup change that isn't backward compatible.
- **MINOR** — new, backward-compatible capability: a new block, a new attribute, a new pattern, a new editor control.
- **PATCH** — bug fix, style tweak, security fix with no new capability.

**When releasing:** bump `Version` in `style.css` and `"version"` in `package.json` together (they must always match), move the `[Unreleased]` entries under a new dated version heading, and start a fresh empty `[Unreleased]` section. See `docs/treeview.md` for the full current structure reference — update it alongside any change that adds/removes/renames a block, pattern, template, or function module.

This file starts tracking from 2026-07-28. Work before that date was ticket-based (see `git log`, tickets `T3`–`T16`) and is not itemized retroactively — `1.0.0` below represents the theme's accumulated state as of this file's creation, not a dated release.

## [Unreleased]

### Security

- Fixed `kotlinskidev/protected-content`: was a static block whose "Use Protection" toggle stored **plaintext** in a `data-original-content` HTML attribute — visible in page source, no real protection. Converted to a dynamic (server-rendered) block using the theme's existing RSA-2048 encryption (`kotlinskidev_encrypt_content()`), producing the same encrypted-span markup the auto-detection system already used. This also immediately fixed an active plaintext leak on the live Contact/Kontakt pages, which were already using the broken block.
- Marked the Search/Szukaj utility pages as `noindex` (Yoast) — they were previously indexable and were surfacing in the "Popular Pages" block, which makes no sense for a search-utility page.

### Added

- FAQ accordion "independent columns" mode: opt-in `kt-faq-independent-columns` / `kt-faq-independent-columns-2/3/4` classes (`src/styles/faq-accordion.scss`, `src/scripts/faq-accordion.ts`), applied per-section via a new "FAQ columns behavior" control (see below). Switches that specific FAQ section from WordPress's native row-locked Grid layout to N independently-growing columns, so opening one item never stretches or leaves empty space in its neighbor's column. Exists as a separate opt-in from the native Grid "Columns" stepper because the two are fundamentally incompatible: CSS Grid always shares row-track height between every item in the same row, by design, with no standards-track escape hatch (`grid-template-rows: masonry` is Firefox-only and not viable) — so a section can have *either* perfectly row-aligned closed items with row-linked growth (native Grid, default) *or* fully independent per-column growth (this opt-in, at the cost of losing exact row alignment, plus a different fill order: items fill one column completely before wrapping to the next, rather than alternating left-right per row). Implemented via a fixed, count-based DOM split rather than CSS multi-column: on page load, `faq-accordion.ts` distributes each `.wp-block-details` into `.kt-faq-column` wrapper `<div>`s (first `⌈count/N⌉` items in column 1, and so on), which the group then lays out with plain `display: flex` + `align-items: flex-start`. Two CSS-only approaches were tried and rejected first — `column-count` with default `column-fill: balance` actively rebalances column heights as content changes, visibly moving items between columns every time an item opens or closes; `column-fill: auto` was tried as a fix but degenerates to a single giant column on an unconstrained (auto) height container, a known Chromium/multicol limitation. The flex + fixed-DOM-split approach sidesteps both: column membership is decided once, by item count, and is structurally immune to any height change.
- `kotlinskidev/faq-layout` block extension (`src/blocks/faq-layout/index.tsx`, `functions/faq-layout.php`): replaces manually typing the `kt-faq-independent-columns[-N]` class above with a real "FAQ columns behavior" dropdown (default grid / independent columns) plus a "columns count" dropdown (2/3/4, shown only in independent mode), added to `core/group`'s native Advanced panel — but only when that specific Group's `innerBlocks` contain a `core/details` child, so it doesn't clutter the Advanced panel of unrelated Group blocks. Follows the same extension pattern already established by `active-link-state` (Advanced-panel control) and `border-gradient` (live canvas preview): `blocks.registerBlockType` registers a `faqLayout: {layout, columns}` attribute on `core/group`, `editor.BlockEdit` renders the controls via `InspectorAdvancedControls`, `editor.BlockListBlock` mirrors the resulting class into the editor canvas live, and a `render_block` PHP filter (`WP_HTML_Tag_Processor`, merged non-destructively into the existing `class` attribute) applies it on the frontend.
- `kotlinskidev/content-block` — new block resolving a `wp_block` reusable-block post by slug (Polylang-translation-aware), for content that needs to live outside a `wp_navigation` post but still be per-language.
- `wp_block` registered as a Polylang-translatable post type (alongside the existing `wp_navigation`), enabling the above.
- `kotlinskidev/simple-grid`: new `tabletColumns` attribute + matching tablet-breakpoint (782–1024px) media query and editor control, alongside the existing `mobileColumns`. Independent 3-tier column control (desktop/tablet/mobile) instead of desktop-or-mobile only.
- `kotlinskidev/protected-content`: new `address` and `other` protection types (in addition to email/phone/text), for arbitrary content that can't be auto-detected by regex.
- `kotlinskidev/popular-pages` / `nav-popular-pages`: new `titleFontSize` attribute with a native `FontSizePicker` control (same component/preset list as core Heading/Paragraph blocks).
- Generic top-level block pass-through added to `kotlinskidev/navigation`'s `list` and `bar` display modes (mirrors what `mega` mode already did via `kotlinskidev_render_nav_extras()`) — any block type now renders in any display mode instead of being silently dropped.
- `kotlinskidev_get_popular_posts()` query now excludes any page carrying Yoast's noindex meta, generally — not just the two pages fixed above.
- SCSS: `kt-not($selectors)` function (`src/styles/mixins.scss`) — builds a `:not()` chain from a SCSS list, so `link.scss`'s dead-link/underline-exception selectors are maintained as lists instead of hand-edited chains.
- Sitewide active-page link state: any link pointing at the page currently being viewed (header/footer nav, mega menu, hamburger overlay, mobile footer bar, `popular-pages`/`nav-popular-pages`) now permanently shows the same gradient-text/underline treatment normally reserved for hover/focus, marked via a new `kt-link-current` class + `aria-current="page"` (`functions/active-link-state.php`, `render_block` filter). Respects the existing `linkHoverEffects` opt-out (`kt-hover-no-link-gradient`) and adds its own per-block "Disable active-page highlight" toggle in the block's native Advanced inspector tab (`src/blocks/active-link-state/index.tsx`), extensible for future related controls.
- Active-page links (and buttons) are now click-disabled by default — `aria-disabled`, `tabindex="-1"`, and `pointer-events:none`, since navigating to the page a visitor is already on does nothing. Mega-menu top-level items that also toggle an open panel (`aria-haspopup="true"`) only get `pointer-events:none` (blocking the wasted self-navigating click when the nav's `linkNavigatesOnClick` is on) — `aria-disabled`/`tabindex` are left off so hover and the keyboard Space-key panel toggle stay fully working.
- New "Active Page Links" section in Settings → Kotlinski.dev → Advanced: two site-wide toggles ("Highlight active-page links" and "Disable current-page link clicks") controlling the two behaviors above, on top of the existing per-block Advanced opt-out.
- Universal gradient-border option: any block with native border support (Group, Row, Stack, Cover, Image, etc. — excludes `kotlinskidev/button`, which already has its own independent gradient-border system) now gets a "Gradient" tab merged directly into WordPress's own Border panel (`InspectorControls` `group="border"`), sourced from the theme's `theme.json` gradient presets via the existing `ColorGradientControl` wrapper. Previously only a solid color was ever selectable for borders — a hard Gutenberg limitation, not a `theme.json` setting. Renders via the same `::before` mask technique as buttons/pills/pagination (`gradient-border` mixin, `src/styles/border-gradient.scss`), live in the editor canvas and on the frontend (`src/blocks/border-gradient/index.tsx`, `functions/border-gradient.php`).
- SCSS: `gradient-border-bg($fill, $gradient, $extra-layer)` mixin (`src/styles/theme-colors.scss`) — the double-background-layer gradient-border technique for elements that can't host a `::before` pseudo-element (native `<input>`/`<select>`), extracted from the existing `.wp-block-search__inside-wrapper:focus-within` rule and reused for `.search-input-field`/`.search-select-field` hover/focus states, which previously fell back to a flat solid-purple border on hover — inconsistent with the rest of the site's gradient-border language.
- `functions/seo-noindex-compat.php`: universal noindex detection across the four most common SEO plugins, replacing the theme's previous Yoast-only checks. `kotlinskidev_apply_seo_noindex_exclusion( $query_args )` detects the active plugin (Yoast, Rank Math, All in One SEO, SEOPress — via their version constants) and returns `$query_args` with the correct exclusion applied for whichever is active: a `meta_query` clause for Yoast (`_yoast_wpseo_meta-robots-noindex`), SEOPress (`_seopress_robots_index`), and Rank Math (`rank_math_robots`, a serialized array — matched with `NOT LIKE`), or a `post__not_in` list for All in One SEO, which stores robots settings in its own `{$wpdb->prefix}aioseo_posts` table rather than post meta and so can't be reached via `meta_query` at all (post IDs cached via transient, matching the existing 15-minute cache pattern in `kotlinskidev_get_popular_posts()`). No-ops safely if no supported plugin is active. Wired into all three existing noindex-exclusion call sites: `kotlinskidev_get_popular_posts()` (`functions/page-view-tracking.php`), `kotlinskidev_enhance_search()` (`functions/blog-topic-manager.php`), and `patterns/search-results.php`.
- FAQ accordion redesign (`kotlinskidev/faq-accordion` pattern, native `core/details` blocks): native triangle marker replaced with an animated `+`/`−` indicator on the right of each `<summary>` (`src/styles/faq-accordion.scss`); open/close now animates via the Web Animations API (`src/scripts/faq-accordion.ts`, ease-in-out, 350ms) instead of the native instant toggle, respecting `prefers-reduced-motion`; items render in a 2-column grid (single-column below `$breakpoint-mobile`) both for new pattern insertions (native Group grid layout) and retroactively on all already-published pages via a `.wp-block-group:has(> .wp-block-details)` CSS rule, since patterns are copied into page content at insertion time and editing the pattern source alone doesn't reach existing content.

### Fixed

- Footer centering: removed a stray `full-width full-container container` className on the footer nav block that was fighting the block's own width constraints (WordPress's own full-bleed CSS trick applied where it didn't belong).
- Footer mobile-viewport alignment: WordPress's constrained-layout system was injecting `margin-left/right: auto !important` on the footer's brand/nav columns, which overrode `align-items: stretch` once the layout dropped to a single stacked column below 782px, causing the nav column to shrink-to-content and center instead of stretching full width.
- Footer brand column width on tablet (782–1024px): reduced from `23.75rem` to `17.5rem` so it doesn't crowd the now-2-column nav grid at that breakpoint.
- Social-link icons rendered as a 36×40px pill instead of a 36×36px circle (classic inline-block baseline/descender-gap quirk) — added `vertical-align: top` to `.wp-block-social-link-anchor`, theme-wide.
- "Want to know more?" CTA social-links row (present on 8 pages: Homepage, Strona Główna, About, O mnie, Contact, Kontakt, Dziękuję, Thank you page): `justifyContent` was set to `"left"` while block alignment was `"center"` — the two conflicted and `left` won, pushing icons flush-left instead of centered.
- Same CTA: the **X** block's URL and the **YouTube** block's URL were swapped (X pointed at a youtube.com URL, YouTube was an unfilled `#`) — corrected using the hamburger/mobile-nav `social-item` entries as the source of truth.
- Removed the `::after` emoji icons (📧/📱) shown after protected email/phone content.
- Search and language dropdown triggers (`<a href="#" class="kt-mega-nav__link">`) had `pointer-events: none` applied by a generic `a[href="#"]` rule meant for genuinely dead links — excluded `.kt-mega-nav__link` so these triggers get a normal pointer cursor like every other dropdown trigger.
- `patterns/search-form.php`: `trim(parse_url($site_url, PHP_URL_PATH), '/')` threw a PHP 8.1+ deprecation notice (`trim(): Passing null to parameter #1`) on every search-results/search-form render, since `parse_url()` returns `null` — not an empty string — when the site's home URL has no path component (this site's does not).
- Search results (`patterns/search-results.php`) were surfacing noindex utility pages (Thank You page, the Search page itself, etc.) as results — the noindex exclusion `kotlinskidev_get_popular_posts()` already applies elsewhere was never applied to search. Fixed in both this pattern's own `WP_Query` (the actual query the results grid renders from) and `kotlinskidev_enhance_search()`'s main-query modification (`functions/blog-topic-manager.php`).
- Gradient Colors formatting (highlight/text) on `kotlinskidev/protected-content` was silently discarded even after being enabled, for any `protectionType` other than `text`:
  - `render.php` ran `wp_strip_all_tags()` on the content before encrypting for every type except `text` — now only `email`/`phone` (which need a clean string for their `mailto:`/`tel:` href) strip tags; `address`/`other`/`text` keep inline formatting intact through encryption.
  - The AJAX reveal handler's `default` case (covering `address`/`other`) rendered the decrypted content with `esc_html()`, escaping any surviving markup back to visible text — it now uses `wp_kses_post()`, matching the `text` type.
  - Even with both of the above fixed, WordPress core's `safecss_filter_attr()` (used internally by `wp_kses_post()` for the `style` attribute) rejects **any** `gradient(...)` CSS value that contains a `var(--...)` reference — which is exactly what every theme.json-based color/gradient preset produces, so every swatch in the "Gradient Colors" picker was silently dropped. Added a `safecss_filter_attr_allow_css` filter (`functions/safe-css-gradient-vars.php`) that recognizes `var()`/`rgba()` nested inside `-gradient()` wrappers as safe, without weakening the existing block on `expression()` or unsafe `url()` schemes (verified both still get stripped).
- Lighthouse-driven accessibility pass across Homepage/About (EN+PL), surfaced by a post-navigation-redesign audit:
  - Mega-nav icon-only items (`kotlinskidev/navigation` `render.php`): the search trigger's `aria-label` fell through to the same empty string as its hidden visible label instead of a real fallback — added a separate `aria_label` field so icon-only items always get accessible text regardless of the editor-saved label.
  - `kotlinskidev/search-panel` trigger button: `$attributes['label'] ?? __('Search', ...)` didn't catch an explicitly-saved empty string (`??` only catches `null`) — same class of bug as above, fixed with an explicit empty-string check.
  - Mega-nav language flag `<img>` had hardcoded `width="20" height="15"` (4:3) while the actual source PNGs are 48×30 (1.6:1), triggering Lighthouse's aspect-ratio check on mobile — corrected to match the real dimensions.
  - Mobile footer nav tap targets were ~40px tall, under the 44px minimum — adjusted `mobile-footer-menu.scss` link height/`min-height` so all four items now measure a clean 44px.
  - Site logo link (`core/site-logo`, rendered inline as SVG for `currentColor` theming) had no accessible name — added a `render_block_core/site-logo` filter (`functions/site-identity.php`) injecting `aria-label="{Site Name} home"` when missing.
- FAQ accordion grid (`.wp-block-group:has(> .wp-block-details)`): `<details>` elements don't reliably honor `align-items`/`justify-items: stretch` in CSS Grid on either axis (a known cross-browser quirk, similar to `<fieldset>`), so same-row items were rendering at their own content width/height instead of filling the row/column — added `width: 100%` and `height: 100%` to `.wp-block-details` (`src/styles/faq-accordion.scss`; a no-op outside grid contexts, since percentage sizing resolves to `auto` against a non-definite-size parent). This also fixed a visible "snap" at the start of the open/close animation: `faq-accordion.ts` was computing the closed-state height from `summary.offsetHeight` alone, which didn't account for the row-stretched height the box actually had — the animation's first frame no longer matches, so the border visibly jumped before transitioning. Now measured from the box's own actual rendered height (`getBoundingClientRect()`, read before/after toggling `open`) instead.
- FAQ accordion column count wasn't actually editor-configurable: every one of the 14 already-published pages embedding FAQ `details` content had its wrapping group saved with `layout:{"type":"constrained"}` (no native grid attribute at all — the 2-column appearance came entirely from the theme's blanket CSS override), so there was no "Columns" control in the block Inspector, and the CSS override's real specificity would have silently ignored per-instance column choices even where native grid layout did exist (e.g. new pattern insertions). Migrated all 14 pages' FAQ group blocks (21 groups total, several pages have multiple FAQ sections) to native `layout:{"type":"grid","columnCount":2}` via the block editor's own data store (`updateBlockAttributes` + `savePost()`, so WordPress regenerates correct markup/classes itself rather than hand-edited serialized content) — preserves the existing 2-column appearance while exposing WordPress's real numeric "Columns" stepper for every FAQ section. The theme's CSS fallback (`src/styles/faq-accordion.scss`) now wraps its `display`/`grid-template-columns` defaults in `:where()` (zero specificity, matching WordPress's own per-instance grid CSS convention) so any per-block column choice — native or future — naturally wins the cascade instead of being overridden; the mobile single-column fallback keeps real specificity since it's a non-negotiable responsive requirement, not an editor preference.
- FAQ accordion open items were silently clipped to their row's closed-sibling height: `.wp-block-details { height: 100% }` (added for row-height uniformity, above) also blocks a grid item's content from growing its row once opened — a known CSS Grid quirk where percentage-height items don't reliably re-trigger row-track growth from their own content. Added `.wp-block-details[open] { height: auto }` so open items size to their real content height (verified: previously clamped to 88px despite ~184px of actual content; now renders at full height) while closed items keep the uniform stretched height.
- FAQ accordion close/open animation had a two-step, out-of-sync jump: the pre-existing `details[open] summary { margin-bottom: 1rem }` rule (`src/styles/components.scss`) ran on its own independent 150ms CSS transition while `faq-accordion.ts`'s height animation ran over 350ms via the Web Animations API — since our JS also flips the `open` attribute at a different point in the sequence than the CSS rule's natural trigger, the two motions landed at different times, producing a visible extra "settle" step instead of one continuous motion. `faq-accordion.ts` now measures and animates `summary`'s `margin-bottom` alongside `details`' `height` in the same synchronized WAAPI call (same duration/easing, same start), and the now-redundant `transition: margin 150ms ease-out` was removed from `components.scss` (the only `<details>` usage in the theme is this accordion, so nothing else depended on it).
  - `kotlinskidev/gallery-lightbox` trigger button's `aria-label` didn't reflect its visible slide-counter badge (`+3` / `01 / 03`), failing WCAG 2.5.3 label-content-name-mismatch — `save.tsx` now appends the counter text to the label.
  - WordPress core's native image-block lightbox trigger buttons ship with no accessible name at all in this WP version, and rely on an Interactivity API `data-wp-bind--aria-label` directive whose bound state is empty until the lightbox is actually opened — `image-lightbox.ts` now applies a fallback `aria-label` (from the image's `alt`) and re-applies it via `MutationObserver` whenever core's directive clears it back out.
  - Cookie-consent banner (Complianz, plugin-rendered) logo link had no accessible name — `cookie-consent.ts` now labels it once the banner mounts, consistent with the file's existing MutationObserver-based patching of the same banner's consent button.
  - Testimonial name headings (`patterns/testimonial-section.php`, `patterns/testimonials-grid.php`) jumped straight from `h2` to `h5` — corrected to `h3`. Same jump (to `h5`/`h6`) existed directly in the published About EN/PL page content (job-title lines) — corrected to `h3`/`h4` there too, since patterns are copied into content at insertion time and aren't retroactively affected by pattern-file edits.
  - Three icon-only "read more" links on the About page (Services/Projects/Contact teaser cards, EN + PL) had no accessible name — added descriptive `aria-label`s directly to the published content.
  - Root cause of several of the above JS fixes appearing to silently not apply: the Asset CleanUp plugin's JS-combine feature was serving a stale cached bundle across rebuilds, and combining `build/main.js` into an aggregate file it does not handle reliably — added `build/main.js` to the plugin's own `combine_loaded_js_exceptions` setting so it loads as its own script instead.
- Homepage "Related Articles" slider (`src/blocks/slider`, the `wp-block-wpe-slider` autoplay carousel): after a manual free-mode drag, autoplay resuming (on `pauseOnMouseEnter`'s mouse-leave, or after the built-in touch-interaction pause) visibly jumped position instead of continuing smoothly from wherever the drag left it. Root cause: Swiper's `activeIndex` bookkeeping doesn't necessarily track the live scroll position during a `sticky:false` free-mode drag, so the subsequent `slideNext()` call used a stale index as its baseline. Added a `swiper.on("autoplayStart"/"autoplayResume", ...)` handler (`src/blocks/slider/swiper-init.ts`) that calls Swiper's own `updateActiveIndex()` (recomputes the index from the actual current translate — the same method Swiper itself uses internally after touch-move) before autoplay continues, so it always reads the real current position first. Verified by desyncing `activeIndex` from the translate directly and confirming the resume event corrects it.

### Performance

- LCP on About (EN+PL) was dominated by a ~1.1s "element render delay" — the browser had the hero image ready almost instantly but couldn't paint it until several render-blocking CSS requests resolved. The theme already had a working `media="print"`-swap technique (`functions/enqueue-scripts.php`) to load `main.css` non-blocking, but it only ever applied to that one handle. Extended it to `wp-block-navigation` (WordPress core's nav-block CSS — the theme's own nav styling already lives in `main.css`) and `wp-pwa-manager-frontend` (plugin CSS), neither of which affects any above-the-fold or Swiper-dependent content. Verified via real (non-simulated) network+CPU throttled traces: LCP dropped from ~1.93s to ~1.67s, CLS unchanged (~0).
  - Deliberately kept render-blocking, after testing: `kotlinskidev-hero-carousel-style`/`-view-style` and `kotlinskidev-gallery-lightbox-view-style`. All three of these `-view-style`/`-init` handles are built from `init.ts` files that start with `import "swiper/swiper-bundle.css"` — they're Swiper's own layout CSS, not decorative polish. Deferring `kotlinskidev-hero-carousel-style` was tried first and measurably broke LCP (1.9s → 4.6s), since the hero image needs Swiper's CSS to become visible at all. `kotlinskidev-gallery-lightbox-view-style` was initially deferred too (currently below-the-fold on every page it's used, so no LCP impact was observed) but reverted on the same principle: the block's own `lazyLoad` attribute already gives editors a per-instance way to mark an above-the-fold usage, and a page-wide CSS-handle defer can't see that — it would silently break any future above-the-fold placement with no connection to the existing lazyLoad system. `banner-carousel` and `slider` are the same Swiper-based pattern and were never touched.
- PHP-level query audit (Query Monitor, live-profiled on About EN: 161 queries baseline, 47 from theme code). Fixed the ones grounded in that trace:
  - `kotlinskidev_resolve_translatable_post()` (`functions/polylang-content-resolution.php`) ran a fresh `get_page_by_path()` on every call with no memoization — added a request-scoped `static` cache keyed by `slug|post_type`. In practice the theme's nav/content-block instances mostly use distinct slugs (footer, header, mobile, language panel), so this is mainly a correctness/defensive fix rather than a large query-count win on its own — it only pays off when the same slug is resolved more than once in a request.
  - `kotlinskidev_get_popular_posts()` (`functions/page-view-tracking.php`) ran its `meta_query` + `orderby: meta_value_num` scan uncached on every load. Wrapped in a 15-minute transient (post IDs only, `fields => 'ids'`, `no_found_rows => true`), reconstructing a normal `WP_Query` via `post__in` on both cache hit and miss so the `->have_posts()`/`->the_post()` loop in `popular-pages/render.php` keeps working unchanged.
    - First attempt at this made total query count measurably *worse* (161 → 174, live-verified, then bisected with a temporary revert to confirm causation) — the `post__in` reconstruction query triggers Polylang's per-post language re-validation (one extra `wp_terms`/`wp_term_relationships` join per post ID) on *every* request, cache hit or miss, which the original single meta_query-shaped query didn't. Fixed by adding `'lang' => ''` to the reconstruction query, since the IDs are already language-resolved by the cached query — Polylang doesn't need to re-check them. This also surfaced a real bug in the first attempt: the cache key didn't include the current language, so EN and PL pages would have shared the same cached post IDs. Fixed by keying on `pll_current_language()` too. Net result, verified live: 161 → 144 queries (warm cache).
  - `kotlinskidev_inline_nav_icon()` was defined identically in two places (`functions/blocks.php` and, guarded by `function_exists()`, `src/blocks/social-section/item/render.php`) and both did a raw uncached `file_get_contents()` on every render. Consolidated to one definition (`functions/blocks.php`) that reuses the theme's existing cached `kotlinskidev_load_svg_content()` (`functions/svg-support.php`); removed the duplicate.
  - `kotlinskidev_get_image_size_cached()` (`functions/filters.php`) was correctly caching but as one transient per unique image URL — a page with 5 unsized images cost 5 separate `wp_options` round trips. Consolidated into a single `kotlinskidev_img_sizes` transient (a map of `md5(url) => size`), loaded once per request and written back at most once, at `shutdown`, only if something new was computed. Per-image invalidation on `edit_attachment`/`delete_attachment` still works (removes just that one entry from the map).
  - `kotlinskidev_get_related_posts()` (`functions/blog-topic-manager.php`) used `orderby: rand`, one of MySQL's worst-performing sort patterns (forces a full-table scan, can't use an index). Replaced with fetching matching post IDs only (`fields => 'ids'`, indexed, no sort), shuffling in PHP, then fetching just the selected subset via `post__in`.
  - Confirmed via the same Query Monitor session: no external HTTP calls happen during page render, and no persistent object cache (Redis/Memcached/APCu) is active — every transient read above still costs a real DB query per call; the fixes reduce query *count* and avoid the worst query *shapes*, but a persistent object-cache backend would still be the single biggest lever available site-wide if added later.

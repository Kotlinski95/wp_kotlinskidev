# Changelog

All notable changes to the kotlinskidev theme are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this theme follows [Semantic Versioning](https://semver.org/):

- **MAJOR** — breaking change: removed/renamed a block or attribute, a template/pattern change that requires editors to re-save affected content, a markup change that isn't backward compatible.
- **MINOR** — new, backward-compatible capability: a new block, a new attribute, a new pattern, a new editor control.
- **PATCH** — bug fix, style tweak, security fix with no new capability.

**When releasing:** bump `Version` in `style.css` and `"version"` in `package.json` together (they must always match), move the `[Unreleased]` entries under a new dated version heading, and start a fresh empty `[Unreleased]` section. See `docs/treeview.md` for the full current structure reference — update it alongside any change that adds/removes/renames a block, pattern, template, or function module.

This file starts tracking from 2026-07-28. Work before that date was ticket-based (see `git log`, tickets `T3`–`T16`) and is not itemized retroactively — `1.0.0` below represents the theme's accumulated state as of this file's creation, not a dated release.

Exists as a separate opt-in from the native Grid "Columns" stepper because the two are fundamentally incompatible: CSS Grid always shares row-track height between every item in the same row, by design, with no standards-track escape hatch (`grid-template-rows: masonry` is Firefox-only and not viable) — so a section can have *either* perfectly row-aligned closed items with row-linked growth (native Grid, default) *or* fully independent per-column growth (this opt-in, at the cost of losing exact row alignment, plus a different fill order: items fill one column completely before wrapping to the next, rather than alternating left-right per row). Two CSS-only approaches were tried and rejected first — `column-count` with default `column-fill: balance` actively rebalances column heights as content changes, visibly moving items between columns every time an item opens or closes; `column-fill: auto` was tried as a fix but degenerates to a single giant column on an unconstrained (auto) height container, a known Chromium/multicol limitation. The flex + fixed-DOM-split approach sidesteps both: column membership is decided once, by item count, and is structurally immune to any height change.

### Performance

- LCP on About (EN+PL) was dominated by a ~1.1s "element render delay" — the browser had the hero image ready almost instantly but couldn't paint it until several render-blocking CSS requests resolved. The theme already had a working `media="print"`-swap technique (`functions/enqueue-scripts.php`) to load `main.css` non-blocking, but it only ever applied to that one handle. Extended it to `wp-block-navigation` (WordPress core's nav-block CSS — the theme's own nav styling already lives in `main.css`) and `wp-pwa-manager-frontend` (plugin CSS), neither of which affects any above-the-fold or Swiper-dependent content. Verified via real (non-simulated) network+CPU throttled traces: LCP dropped from ~1.93s to ~1.67s, CLS unchanged (~0).
  - Deliberately kept render-blocking, after testing: `kotlinskidev-hero-carousel-style`/`-view-style` and `kotlinskidev-gallery-lightbox-view-style`. All three of these `-view-style`/`-init` handles are built from `init.ts` files that start with `import "swiper/swiper-bundle.css"` — they're Swiper's own layout CSS, not decorative polish. Deferring `kotlinskidev-hero-carousel-style` was tried first and measurably broke LCP (1.9s → 4.6s), since the hero image needs Swiper's CSS to become visible at all. `kotlinskidev-gallery-lightbox-view-style` was initially deferred too (currently below-the-fold on every page it's used, so no LCP impact was observed) but reverted on the same principle: the block's own `lazyLoad` attribute already gives editors a per-instance way to mark an above-the-fold usage, and a page-wide CSS-handle defer can't see that — it would silently break any future above-the-fold placement with no connection to the existing lazyLoad system. `banner-carousel` and `slider` are the same Swiper-based pattern and were grouped with the above by assumption at the time, not individually tested. Revisited `slider` (`wpe-slider-style` handle) later: unlike `hero-carousel`, its only current usage (the homepage's "Related Articles" section) sits ~2900px down a ~900px viewport — nowhere near the LCP-critical path. Added it to the existing `$deferred_handles` array (same `functions/enqueue-scripts.php`) and verified via a real trace: the `RenderBlocking` insight for it disappeared entirely, LCP unchanged (479ms), CLS unchanged (0.01), slider renders and functions identically once scrolled into view. `banner-carousel` remains untested/untouched — no live instance on the site to verify against either way.
  - Lighthouse desktop also flagged `wordpress-pwa-manager`'s `frontend.js` in the network-dependency critical path — a plugin file, off-limits to edit directly, but it renders with a plain synchronous `<script>` tag (no `async`/`defer`). Its own code already wraps all initialization in a `DOMContentLoaded` listener (confirmed by reading the actual script this session), so deferring its *execution* changes nothing behaviorally — only when it starts. Added `kotlinskidev_defer_deferrable_scripts()` (`functions/enqueue-scripts.php`, `script_loader_tag` filter targeting the `wp-pwa-manager-frontend` handle only) to inject `defer` from the theme side, without touching the plugin's own files. Verified live: PWA Manager still logs `"Initializing PWA Manager..."` and runs identically post-change.
  - Generalized the hardcoded `wpe-slider-style` defer entry into a reusable, per-page-dynamic mechanism for *any* block, since a flat handle array can't express "defer this, except when an editor places it above the fold on a specific page": `functions/deferred-block-assets.php` — `kotlinskidev_get_deferrable_block_assets()` is a filterable registry (block name → style/script handle) that new blocks register into via `kotlinskidev_deferrable_block_assets`, rather than hand-editing `enqueue-scripts.php` each time; a `kotlinskidevAboveFold` boolean block attribute (added only to registered-deferrable blocks, mirroring `border-gradient`'s `supports.border`-gated pattern rather than `active-link-state`'s apply-to-everything one) lets an editor opt a specific instance out of deferring; `parse_blocks()` recursively scans the current singular post's content for any instance with that flag set, cached in a transient keyed by `post_id . '_' . post_modified_gmt` (same auto-invalidating-by-edit pattern already used for `critical.js`'s cache key) so the scan only re-runs when the post actually changes, not on every visitor's page load; a request-scoped `static` cache on top avoids re-computing within a single request. `wpe/slider` was the first registration; also added `kotlinskidev/gallery-lightbox` (`kotlinskidev-gallery-lightbox-view-style`, confirmed below-the-fold on its current usage, verified live post-change: LCP/CLS unchanged, lightbox still opens and functions) and `kotlinskidev/banner-carousel` (two handles — `kotlinskidev-banner-carousel-style` + `kotlinskidev-style-banner-carousel-style`, hence `style` now accepts an array — but this block has no live page instance to test against, same caveat as before). Initially left `kotlinskidev/hero-carousel` unregistered on the reasoning that its default-deferred polarity was backwards for a block that's virtually always the page's hero — but that missed a simpler fix: registry entries can now declare a **per-block default** for `kotlinskidevAboveFold` (`default_above_fold`) instead of the mechanism only ever defaulting to `false`. Registered `kotlinskidev/hero-carousel` (`kotlinskidev-hero-carousel-style` + `-view-style`) with `default_above_fold: true`, so it reproduces today's always-render-blocking behavior exactly — with the option to flip a specific instance off if a future page ever places it somewhere genuinely below the fold. Required two correctness fixes to actually implement per-block defaults correctly, not just cosmetically:
    - WordPress's block serializer omits attributes from saved markup when they match the schema's `default` — so existing hero-carousel instances (saved before this attribute existed) have **no** `kotlinskidevAboveFold` key at all in their stored content, not an explicit `false`. `kotlinskidev_scan_blocks_for_above_fold()` now falls back to the per-block registry default (via `array_key_exists()`, not `!empty()`) whenever the attribute is absent, rather than assuming absence means `false`. Verified directly: `en/about/`'s hero-carousel, which has never had this attribute serialized, correctly resolved to non-deferred purely from the registry default — zero content migration needed.
    - The transient cache is keyed by `post_id . '_' . post_modified_gmt` — content-based, not code-version-based. Adding `hero-carousel` to the registry meant every already-cached above-fold transient for a page using it was now stale (computed under logic that didn't know that block existed yet), and would have **silently deferred hero-carousel's CSS on next load** until each transient's natural expiry — the exact regression this whole feature exists to prevent. Manually cleared all `kotlinskidev_above_fold_*` transients after the code change to close that window immediately rather than leaving it to expire over the next week.
    - Also did not register `kotlinskidev/scroll-section`: its CSS is currently merged into an Asset CleanUp combined bundle rather than served as an individual `<link>`, so the `media="print"` swap isn't proven to apply cleanly to it, and Lighthouse has never actually flagged it as render-blocking in the first place.
    - Verified live on `en/about/` (uses both hero-carousel and gallery-lightbox simultaneously): hero-carousel correctly stays non-deferred (`media='all'`, no swap), gallery-lightbox correctly stays deferred (`media='print'` swap) — same page, two different per-block defaults, both resolved correctly. LCP 969ms / CLS 0.01, matching the pre-change baseline (958ms / 0.01) within noise.
  The editor-side toggle (`src/blocks/above-fold/index.tsx`, `InspectorAdvancedControls`) reads the deferrable-block-name list from `kotlinskidevDeferrableBlocks` (localized from the same PHP registry, single source of truth) so it only appears on blocks that actually have something to defer. Verified end-to-end via `wp eval` (`parse_blocks`/`serialize_blocks`, not string patching): toggling the attribute produces a new transient keyed correctly, the CSS `<link>` correctly drops the `media="print"` swap when marked above-the-fold and correctly re-applies it when reverted — confirmed on real post content, not a synthetic test.
- PHP-level query audit (Query Monitor, live-profiled on About EN: 161 queries baseline, 47 from theme code). Fixed the ones grounded in that trace:
  - `kotlinskidev_resolve_translatable_post()` (`functions/polylang-content-resolution.php`) ran a fresh `get_page_by_path()` on every call with no memoization — added a request-scoped `static` cache keyed by `slug|post_type`. In practice the theme's nav/content-block instances mostly use distinct slugs (footer, header, mobile, language panel), so this is mainly a correctness/defensive fix rather than a large query-count win on its own — it only pays off when the same slug is resolved more than once in a request.
  - `kotlinskidev_get_popular_posts()` (`functions/page-view-tracking.php`) ran its `meta_query` + `orderby: meta_value_num` scan uncached on every load. Wrapped in a 15-minute transient (post IDs only, `fields => 'ids'`, `no_found_rows => true`), reconstructing a normal `WP_Query` via `post__in` on both cache hit and miss so the `->have_posts()`/`->the_post()` loop in `popular-pages/render.php` keeps working unchanged.
    - First attempt at this made total query count measurably *worse* (161 → 174, live-verified, then bisected with a temporary revert to confirm causation) — the `post__in` reconstruction query triggers Polylang's per-post language re-validation (one extra `wp_terms`/`wp_term_relationships` join per post ID) on *every* request, cache hit or miss, which the original single meta_query-shaped query didn't. Fixed by adding `'lang' => ''` to the reconstruction query, since the IDs are already language-resolved by the cached query — Polylang doesn't need to re-check them. This also surfaced a real bug in the first attempt: the cache key didn't include the current language, so EN and PL pages would have shared the same cached post IDs. Fixed by keying on `pll_current_language()` too. Net result, verified live: 161 → 144 queries (warm cache).
  - `kotlinskidev_inline_nav_icon()` was defined identically in two places (`functions/blocks.php` and, guarded by `function_exists()`, `src/blocks/social-section/item/render.php`) and both did a raw uncached `file_get_contents()` on every render. Consolidated to one definition (`functions/blocks.php`) that reuses the theme's existing cached `kotlinskidev_load_svg_content()` (`functions/svg-support.php`); removed the duplicate.
  - `kotlinskidev_get_image_size_cached()` (`functions/filters.php`) was correctly caching but as one transient per unique image URL — a page with 5 unsized images cost 5 separate `wp_options` round trips. Consolidated into a single `kotlinskidev_img_sizes` transient (a map of `md5(url) => size`), loaded once per request and written back at most once, at `shutdown`, only if something new was computed. Per-image invalidation on `edit_attachment`/`delete_attachment` still works (removes just that one entry from the map).
  - `kotlinskidev_get_related_posts()` (`functions/blog-topic-manager.php`) used `orderby: rand`, one of MySQL's worst-performing sort patterns (forces a full-table scan, can't use an index). Replaced with fetching matching post IDs only (`fields => 'ids'`, indexed, no sort), shuffling in PHP, then fetching just the selected subset via `post__in`.
  - Confirmed via the same Query Monitor session: no external HTTP calls happen during page render, and no persistent object cache (Redis/Memcached/APCu) is active — every transient read above still costs a real DB query per call; the fixes reduce query *count* and avoid the worst query *shapes*, but a persistent object-cache backend would still be the single biggest lever available site-wide if added later.
- `kotlinskidev/protected-content` reveal (`src/scripts/protected-content.ts`, `functions/protection-helpers.php`): every protected element (email/phone/address, etc.) fired its own independent `admin-ajax.php` request on page load — a contact footer with all three types cost 3 separate round trips to `admin-ajax.php`, which loads a full WP bootstrap per request. Found via a Chrome DevTools trace while investigating whether the Complianz cookie banner was a Lighthouse bottleneck (it wasn't — its CSS/JS are already non-render-blocking and it never shifts layout, since the banner is `position: fixed`); these decrypt calls turned out to be the real, unrelated cost. Reworked to: (1) batch — `kotlinskidev_ajax_decrypt_content` now accepts a JSON-encoded `items` array and decrypts them in one request/response instead of one call per element; (2) lazy-load — elements are no longer decrypted eagerly on `DOMContentLoaded`, each is registered with a shared `IntersectionObserver` (`200px` root margin) and only queued once it's about to enter the viewport, with same-tick intersections (e.g. a footer's email+phone+address appearing together on scroll) coalesced into a single request via a 50ms debounce. Above-the-fold protected content still resolves immediately, since its observer fires on the very next frame.
